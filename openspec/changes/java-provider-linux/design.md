## Context

`unify-java-provider` created the single Java provider with a backend trait; `provider-java-swing` puts the agent behind that trait and proves it on Windows, where a Java window enters the tree because the JAB backend enumerates native top-levels itself and the platform's `JavaClassifier` answers "is this a JVM?". Neither mechanism exists on Linux. This change is the Linux bring-up of the provider — not of a toolkit adapter.

Part of the problem is already solved elsewhere: **finding the JVMs that already carry an agent** is `handshake::discover()` from `java-agent-core`, which scans the per-user agent directory and is platform-neutral, and **which windows such a JVM has** is something the agent knows from inside the process. What is open is everything about a JVM that has *no* agent yet — because that is the one nothing on Linux can currently see — plus how an agent-served window's *native identity* is obtained.

One qualification on the middle claim, measured after this change was written: the agent knows the windows of *its own* AWT `AppContext`, not of the JVM, and a runtime that gives each application its own — Java Web Start, applets — therefore leaves it seeing none. [`java-agent-web-start`](../java-agent-web-start/design.md) fixes that in the agent, and this change simply inherits the fix; nothing here has to do anything about it. It matters for the ordering, though, because on Linux there is no second channel to notice the gap through (see Risks).

## Goals / Non-Goals

**Goals:**

- `crates/provider-java` builds and is linked on Linux, with the JAB backend target-gated out.
- An agent-carrying JVM's windows appear as top-level nodes on X11, with working geometry and window patterns.
- **A Java application that carries no agent is attached automatically on Linux, as it is on Windows** — so `java-provider`'s existing *Automatic attachment to detected JVMs, on by default* requirement is honoured on the platform this change adds, rather than inherited unmet.
- The Swing fixture served through the agent on X11 — Swing on Linux without `java-atk-wrapper`.

**Non-Goals:**

- Toolkit adapters. The Swing reader is `provider-java-swing`; JavaFX and SWT are their own changes. This change makes the *provider* work on Linux; whichever adapters exist then work there.
- A Linux **toolkit discriminator** (`native:JvmToolkit`) and the `JavaClassifier` capability that would carry it. "Is this process a JVM?" *is* used here (decision 5) and needs no classifier — `platynui_java_agent::jvm::process_runs_jvm` already answers it from `/proc/<pid>/maps`. What stays out is telling Swing from SWT from JavaFX from outside, which has no X11 equivalent of a window class and which nothing here needs: the agent classifies its own toolkit from inside once it is in.
- Native Wayland. See decision 3.
- Changing anything about Windows — including its attach-candidate source, which stays JAB-fed even though decision 5's mechanism would serve it too.

## Decisions (proposed) and Open Questions

1. **Where the top-level's native identity comes from (narrowed — see decision 5).** Two sources were framed as alternatives here, with a measurement to pick one. They are not alternatives: they answer different questions, and once automatic attachment is in scope only one of them can answer the harder one.

    - **(a) The agent reports it.** `sun.awt.X11.XBaseWindow#getWindow` (and its per-JDK forms, with the `--add-opens` matrix on 9+) yields the X11 window id in-process. This answers *"what is the native identity of this window?"* for a JVM that **already has an agent** — which is every window this backend serves, so where it works it is the cheapest and most exact answer available, and it makes `provider-java-swing` decision 5's PID+geometry fallback Windows-only by construction.

      The opening mechanism is `ModuleAccess`, which already requests `sun.awt.X11` on every platform for exactly this, and it keeps working now that the agent's classes are bootstrap-defined ([`java-agent-web-start`](../java-agent-web-start/design.md) decision 1) — verified on JDK 21 by reading the Windows handle through the same path. Run the measurement below with the **shipping** artifact rather than an ad-hoc agent, so the loading model under test is the one that will be deployed.
    - **(b) `WindowManager` gains an enumeration method**, answered on X11 from `_NET_CLIENT_LIST`/`_NET_CLIENT_LIST_STACKING` — which `platform-linux-x11` already reads internally but does not expose. Keep it in the platform layer: a provider growing its own `x11rb` client would break the rule that keeps `provider-atspi` free of windowing dependencies and working identically on X11 and Wayland.

    **(b) is now unconditional**, because it is the only thing that can answer *"which windows exist, and which processes own them?"* for a JVM that has **no agent yet** — the question automatic attachment is made of, and one an in-process agent cannot answer by definition, since there is no agent in there to ask. The earlier instruction "do not build (b) speculatively" is withdrawn: it is not speculative any more.

    The measurement therefore no longer decides *whether* (b) exists, only whether (a) is used **in addition**, for the identity of agent-served windows. That is still worth measuring — an in-process answer is exact where a `_NET_CLIENT_LIST` correlation is a match — but nothing is blocked on it.

2. **Routing on Linux is a single-backend case, and stays one.** There is no JAB backend to compete with, so the `Enumeration` reshape `provider-java-swing` needs for agent-vs-JAB selection is a Windows concern and must not leak here. The criterion needs no classifier: `handshake::agent_present(pid)` is public and platform-neutral, so "is there an agent in this JVM?" is answerable on Linux today without the platform bundle carrying a `JavaClassifier`.

    Routing and *candidate discovery* are separate questions with separate answers, and conflating them is what hid the gap this change closes. Routing asks "which backend serves this window?" and on Linux the answer is trivially "the only one". Candidate discovery asks "which JVMs should be offered an agent?" — and that one has no answer on Linux at all until decision 5 gives it one.

3. **Wayland is reached through XWayland, deliberately (decided).** The shipped JDKs have no AWT Wayland backend (Project Wakefield is not in), so a Swing application on a Wayland session runs as an X11 client through XWayland — and `xwayland-satellite` covers compositors that ship none. The X11 path therefore covers Wayland for Java, and building a second path would be building for a JDK that does not exist yet. What this change owes is a verified statement of *where* the X11 window id is valid (the XWayland display, not the Wayland compositor) and the note in the docs, not a second implementation.

4. **Absence stays inert (decided, inherited).** The provider on Linux with no agent anywhere contributes no nodes and logs nothing beyond what `handshake::discover()` already costs — a directory scan that finds nothing. This is the same inert-absence rule `java-provider` already states for a missing backend; it matters more here because on Linux there is no JAB fallback whose absence would be noticed instead.

5. **Where attach candidates come from, and who owns the question (new).** The Java provider offers the agent to the JVMs behind the Java windows a pass saw: `JavaProvider::get_nodes` calls `consider_attaching(&sweep.java_processes)`, and `java_processes` is filled **only by backends that enumerate windows** — which today means JAB, and only on Windows. Target-gating JAB out (task 2.1) therefore removes the candidate list entirely, and `auto_attach` would stay on by default while never being able to fire. That is not a Linux quirk to document; it is `java-provider`'s *Automatic attachment to detected JVMs, on by default* silently unmet on a platform this change adds. So Linux gets a candidate source:

    - **The router asks, not the backend.** The agent backend's shape is settled and correct — "it does not enumerate windows at all, it finds agents" — and the fix must not blur it. `JavaProvider` already receives the `WindowManager` in `set_window_manager` (it forwards it to the backends and keeps nothing); it keeps a handle and fills `java_processes` from decision 1(b)'s enumeration. Only the router can do this, for the same reason it already owns `consider_attaching`: only it sees all the backends.

      **The condition is which backends exist, not what a pass found.** The obvious formulation — "when no backend contributed candidates" — is wrong, and quietly so: on Windows, a pass in which JAB happens to see no Java window satisfies it too, and the router would switch Windows onto the window-derived source, which the Non-Goals forbid. It is also a bug that would not show up, because it is masked today by `platform-windows` not implementing the enumeration — an accident, and one this design argues against relying on, since "list native top-levels" is useful beyond Java and somebody will implement it. So the backend trait declares it statically: a backend says whether it enumerates native windows, and the router consults the window manager only when none of its backends does. Then a pass that finds nothing means nothing was there.
    - **Window → process id, by the rule this repo already wrote down.** `dev-docs/java-toolkits.md` settles it: prefer the **X-Resource extension v1.2** (`XResQueryClientIds` with the `LocalClientPID` mask), because the X server derives the pid from the connection's socket credentials and it is therefore authoritative even for a client that sets no property; fall back to EWMH `_NET_WM_PID` only when `WM_CLIENT_MACHINE` matches the local host, since the property is client-claimed and meaningless for a remote X client. Do not invent a second rule here.
    - **JVM filter.** `platynui_java_agent::jvm::process_runs_jvm` answers it from `libjvm.so` in `/proc/<pid>/maps`, is public and already used by the attach transport. Its `None` ("could not answer") must stay non-blocking exactly as `attach::load_agent` already treats it — only a definite `Some(false)` excludes a pid. A window whose owner cannot be probed is a candidate; the attach will fail cheaply and be logged if it is not a JVM.
    - **The quiescence boundary is not negotiable.** `java-agent` requires that "machine-wide JVM enumeration SHALL NOT be performed at any time; only processes owning windows already under consideration are relevant". Enumerating *windows* and deriving their owners satisfies that; walking `/proc` for JVMs does not. The distinction is easy to lose in implementation because the second is simpler, so it is stated as a constraint rather than left to taste — a JVM with no window is never probed, never attached, never noticed.

    Windows keeps its JAB-fed candidate list in this change (Non-Goals), even though this mechanism would serve it too and would remove its odd dependency — that a bridge DLL must be findable before the *agent* path can be offered a pid at all. Making that switch is a Windows behaviour change and belongs to whoever makes it deliberately.

## Risks / Trade-offs

- [The change grows a core trait change, now unavoidably] → the enumeration method on `WindowManager` is no longer contingent on a measurement (decision 1), so this change definitely touches `platynui_core`. That is the right place for it: "list native top-levels" is a question any provider correlating with the windowing system has, not a Java one. Scoped to X11 first; other backends report `CapabilityUnavailable` as they already do for unimplemented window operations — and a backend that does so simply has no automatic attachment, which is today's behaviour everywhere but Windows.
- [`_NET_CLIENT_LIST` is a window-manager convention, not a guarantee] → it is EWMH, so a session without a conforming window manager has no list and the enumeration answers empty. The consequence is bounded and honest: no candidates, hence no automatic attachment, hence exactly today's behaviour — a JVM launched with `-javaagent` is still served, because that path never needed the list. Under XWayland the list belongs to the XWayland display's window manager, which is what decision 3's verification has to confirm rather than assume.
- [`_NET_WM_PID` is client-claimed] → a window can name any pid, and PlatynUI would then offer an agent to a process that does not own it. This is why the X-Resource extension is the preferred source and why the fallback is gated on `WM_CLIENT_MACHINE` (decision 5). Attaching to the wrong process is not a cosmetic error: it injects an agent into something the user never pointed at.
- [An agent-served window has no native representation to fall back to] → that is the premise, not a regression: without an agent the window is invisible to PlatynUI on Linux today. The consequence to state in the docs is that on Linux the agent is not an upgrade over a native path, it *is* the path.
- [No fallback also means no second opinion, so an agent-side blind spot is total here] → the concrete case is the one measured in [`java-agent-web-start`](../java-agent-web-start/design.md): a Java Web Start application's windows live in their own `AppContext` and the agent saw none of them. On Windows that failure is cushioned — JAB still serves the window, so the symptom is reduced fidelity. On Linux the same failure is an application that does not appear at all, with nothing to indicate that it should. This does not add work to this change, which inherits the fix; it argues for landing that change first, and for the Linux lane covering a JVM whose UI is *not* in the agent's own `AppContext` rather than only the plain fixture.
- [Linux lane cost] → the X11 acceptance session already exists (`just test-acceptance-x11`); what is new is the Swing fixture launched inside it and the suite tagging.

## Migration Plan

Additive. On Windows nothing changes; on Linux the provider goes from absent to present, so a session that previously saw nothing for a Java application starts seeing it — which is the point. Rollback: `providers.java.enabled = false`, or reverting the link-macro arm so the crate is not registered.

## Verification items (approach decided; mechanics to confirm)

- **X11 handle reliability** (1): does `sun.awt.X11.XBaseWindow#getWindow` yield the top-level X11 window id across JDK 8 / 17 / 21, on bare X11 **and** under XWayland, and what `--add-opens` does each need? This decides whether the agent's in-process answer is used for identity **in addition to** the platform enumeration; it no longer gates the enumeration itself.
- **Geometry agreement** (1): the agent's reported bounds against `GetWindowRect`'s X11 equivalent for the same window, so the physical-pixel wire contract is confirmed on a second windowing system.
- **Candidate discovery on X11** (5): an agent-less Swing JVM's window is enumerated, its owner resolved via `XResQueryClientIds`, recognised as a JVM, attached, and served **in the same enumeration pass** — the end-to-end proof that automatic attachment is real on Linux and not merely configured on.
- **Window → pid trust** (5): the X-Resource answer and `_NET_WM_PID` agree for the fixture; a window claiming a foreign pid is not followed. Verifiable by setting `_NET_WM_PID` to a pid the window does not belong to.
- **Enumeration under XWayland** (3, 5): the client list and the pid resolution work against the XWayland display, so the Wayland story stays "the X11 path covers it" rather than an untested assumption.
- **Quiescence holds** (5): a JVM with no window is never probed and never attached, and no `/proc` sweep happens — the enumeration is of windows, and only their owners are looked at.
- **Inert absence on Linux** (4): a session with no agent anywhere comes up normally and contributes no Java nodes.
