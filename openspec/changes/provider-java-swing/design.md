## Context

This is the "agent half" of the Java-toolkit map in [`dev-docs/java-toolkits.md`](../../../dev-docs/java-toolkits.md); the "detection half" is `java-app-classifier` (stage 1). It is captured as **forward design**: transport, discovery, and the data model are decided below; the remaining open questions (coordinate spaces, window-handle resolution, threading details) are consolidated at the end and gated behind a spike. Treat the tasks as a roadmap that starts with that spike, not a settled plan.

Toolkit scope: this change builds the shared infrastructure **and the Swing/AWT adapter**; the JavaFX and SWT adapters are separate follow-up changes (`provider-java-javafx`, `provider-java-swt`) that reuse the wire, injection, and routing decided here. Structurally the agent lands as a **backend of the single Java provider** established by `unify-java-provider` (JAB is the other backend) — which is why this change needs no `window_claims` semantics change at all.

The consent/fidelity axis is the reason this coexists with the native providers rather than replacing them:

```
              zero consent        one-time consent       per-launch consent
   Fidelity   ├ JAB (Win) ──────────────────────────────────────────────┤
     low      │ AT-SPI (SWT)      │                                       │
              │ AX (Mac)          │      agent (full, all platforms) ─────┤
     high     └───────────────────┴───────────────────────────────────────┘
```

## Goals / Non-Goals

**Goals:**

- Full-fidelity Java trees (real identity, correct bounds, working table cells) as ordinary PlatynUI nodes — same XPath, Inspector, picker.
- Keyword-free: routing is automatic via the classifier + the Java provider's backend selection; the user only writes locators.
- One provider (RPC client) across Windows/Linux/macOS, one agent artifact.

**Non-Goals:**

- Replacing the JAB backend / native providers — they remain the zero/low-consent floor.
- Silent instrumentation — auto-attach is opt-in and off by default.
- A general bytecode-instrumentation framework — the agent reads accessibility/scene models, it does not rewrite app logic.
- Machine-wide JVM enumeration (`jps`/`hsperfdata`-style listing) — only window-owning JVMs are in scope; see decision 5.
- **This change covers Swing/AWT only** (decided). The JavaFX and SWT adapters are the follow-up changes `provider-java-javafx` and `provider-java-swt`; the JavaFX-on-Linux gap stays open until the FX adapter ships. This holds scope tight against the one toolkit where the fidelity pain is proven (JTable) and lets the wire/transport/lifecycle harden before a second toolkit is added.
- **Mixed-toolkit trees** (`JFXPanel` hosting FX inside Swing, `SwingNode` hosting Swing inside FX, the `SWT_AWT` bridge) are deferred to a proposal of their own, written once at least two adapters exist. Consequence for this change: the single-toolkit-per-JVM assumption baked into detection and the handshake file is **deliberately provisional, not an invariant** — decisions 1/1a keep the wire shaped so lifting it later needs no format break (`toolkits` is a list).

## Decisions (proposed) and Open Questions

1. **One PlatynUI agent JAR, both entry points, toolkit self-detection.** The agent is a single PlatynUI-owned artifact with `premain` (launch) and `agentmain` (attach) entry points and `toolkit=auto` self-detection — from inside the JVM the active toolkits are unambiguous (a `javax.swing` window hierarchy vs. a JavaFX `Stage` vs. an SWT `Display`), so the agent is the authoritative classifier that host-side detection defers to. Self-detection reports the **set** of active toolkits; in this change the only supported entry is Swing/AWT, and a JVM running several toolkits at once is the deferred mixed-toolkit case (see Non-Goals). The attach driver (a small main class around `VirtualMachine.attach`/`loadAgent`) ships **inside the agent JAR** — no separate attacher artifact — and reports "attach failed" and "agent rejected inside the target" (e.g. a sandboxed-JNLP `SecurityManager`) as distinct exit codes so failures stay diagnosable. That driver is only the convenience path for hosts that happen to have a JDK (`VirtualMachine` lives in `jdk.attach`); hosts without one are served by the native transport of decision 5, so **no foreign attacher binary is bundled**. The agent also exposes point-hit-test/highlight endpoints for the picker — in-JVM hit-testing is trivial (`SwingUtilities.getDeepestComponentAt`) and closes the table-picker gap JAB cannot.

1a. **Control plane / data plane split; data plane = loopback TCP + handshake file.** Injection (`-javaagent` or Attach) is a **one-time control plane**; the running traffic flows over the agent's **own data plane**. The two must not be conflated — the JDK's attach mechanism is a command channel only (`load`, `properties`, dumps; short-lived sessions, one listener thread), and on Windows every attach is an `OpenProcess`+`CreateRemoteThread` into the target (EDR-visible), so it is used exactly once to load the agent and never for reads. (Prior art contrast: JAB *fuses* control and data into Win32 messaging — hidden-window rendezvous, then synchronous `SendMessage`/`WM_COPYDATA`/shared memory — which is why it is zero-config but Windows-only, blocks callers on a hung JVM, and needs UIPI workarounds. We keep its good idea, zero-config rendezvous, in portable form.)

    - **Transport:** the agent binds `127.0.0.1:0` (OS-chosen ephemeral port) with a plain `ServerSocket`. This is forced, not merely chosen: the agent must run on **Java 8** targets, where Unix domain sockets don't exist yet (JEP 380 = Java 16) and a named-pipe *server* is impossible in pure Java — loopback TCP is the only all-platform Java-8 server option. Framing: newline-delimited JSON-RPC 2.0; short client-side per-call timeouts, never open-ended socket reads. A **server-initiated notification frame** (a message without an `id`) is part of the wire from day one — v1 uses it only to publish the UI-generation counter (decision 7), so later `event_capabilities` need no protocol break. The handshake enforces an **exact provider↔agent version match** (decided): agents cannot be unloaded, so a mismatch simply **aborts** the connection with a diagnostic naming both versions and the fix (restart the JVM with the current agent) — simplest rule, no silent drift, and no semver-compatibility windows planned; delivery keeps versions aligned at install time instead (decision 9's exact pin).
    - **Handshake file (rendezvous + auth + discovery in one):** on startup the agent writes `<per-user runtime dir>/platynui/agent-<pid>` (directory `0700`/owner-only) containing `{ port, token, toolkits, agentVersion, pid }`, and deletes it on shutdown. `toolkits` is a **list** from day one — in this change it always has exactly one entry (`"swing"`), but the later mixed-toolkit proposal then needs no handshake-format break. The provider discovers agents by reading these files and must present the random `token` in the connection handshake. This one mechanism solves: port collisions (the OS picks), discovery for **user-launched** `-javaagent` targets (no port argument needed; works even with `-XX:+DisableAttachMechanism`), authentication on multi-user hosts (loopback TCP alone is connectable by any local user — terminal servers are common in enterprise Java), and the classifier's "agent present in this JVM?" signal (file exists + ping). The token is deliberately **not** passed as a `-javaagent` argument (`/proc/<pid>/cmdline` is world-readable on Linux); the agent generates it and only the `0700` file carries it.

2. **Data model: component-tree spine + accessibility enrichment + virtual accessible subtrees — full surface from the start (decided).** The wire carries everything both levels offer (not a minimal set): direct properties incl. `Component.getName()`, client properties, model data (`TableModel` bulk reads), the complete state set, and the accessible view — the exact field list is pinned against the fixture in the spike, but the scope decision is "all of it". The agent reads **both** levels the JVM offers, in a fixed relationship:

    - **Spine = the toolkit instance tree** (`Window`→`Container`→`JComponent`; `Stage`→`Scene`→`Node`; `Display`→`Shell`→`Control`): complete, deterministic, carries geometry — and it is the only level that has `Component.getName()` (the classic automation id JAB could never see), direct model access (`TableModel` bulk reads instead of per-cell calls), and semantic actions. For JavaFX and SWT it is the only level at all (neither implements `javax.accessibility`).
    - **Enrichment = the accessible view per node** (`AccessibleContext` where present: accessibleName/role/description/states) — so locators written against JAB's `accessibleName` keep working unchanged, and apps that only annotated accessibility stay addressable.
    - **Virtual accessible subtrees where components end:** a `JTable`'s cells are not components but `AccessibleJTableCell` wrappers — *correct* in-process (name, `getCellRect` bounds, selection) — and custom-drawn components may expose structure only through accessibility; the agent grafts these as child nodes of the spine.

    Actions keep PlatynUI's philosophy: real input (pointer/keyboard) via correct bounds stays platform-level; the agent backs tree/attributes/bounds/hit-test plus selected patterns (Focusable via `requestFocus`), mirroring the JAB provider's pattern surface. Per the `text-input-policy` capability (`remove-programmatic-set-text`) the agent exposes **no** text write: TextEditable is a capability marker derived from the toolkit's editable state (plus `IsReadOnly`), and text is typed via synthesized keyboard input like everywhere else.

2a. **Where PlatynUI adds value = the mapping layer.** The provider maps agent elements → normalized role/namespace, `native:*` attributes, patterns, and — crucially — **stable identity-based `RuntimeId`s**: the agent holds real Java object references, so unlike JAB's enumeration-index scheme, ids can be identity-stable. Element ids are **agent-assigned registry ids backed by weak references** — not Java `identityHashCode` (collision-prone, reused after GC) and not strong-ref caches (which would leak every component ever touched).

2b. **Coordinates: the agent emits physical desktop pixels (decided).** The conversion happens in the JVM (via `GraphicsConfiguration` transforms), where the toolkit's own scaling knowledge lives — Java 8 (already physical) and Java 9+ (per-monitor user-space) are normalized at the source, and the provider stays dumb. No provider-side calibration heuristic (the inverse of what JAB forced on us). The spike verifies the conversion on a HiDPI-scaled monitor across JDK 8/17/21.

3. **Routing: internal backend selection in `provider-java` (decided; supersedes the earlier rank-based-claims design).** With `unify-java-provider` in place there is exactly one Java claimant, so `window_claims` stays **boolean and untouched**. The classifier (stage 1) gains an "agent present?" signal (the handshake file); the Java provider's router serves a JVM window via the **agent backend when an agent is present**, else via the JAB backend. Mid-session robustness — the property the abandoned ranking design existed for — comes for free: when an agent appears in an already-running JVM (auto-attach, late `-javaagent` discovery), the router switches the serving backend on the next enumeration pass; the *claim* never changes, so there is no registry protocol and no consumer update anywhere.

4. **Port / instance discovery — DECIDED: the handshake file (decision 1a).** The agent binds an OS-chosen port and publishes it (with the auth token) in the per-user `agent-<pid>` file; the provider discovers agents by scanning that directory. No port arguments, no collisions across concurrent target JVMs, no repeated attach round-trips just to read a system property (which on Windows would mean a fresh `CreateRemoteThread` per poll). *Rejected alternatives:* fixed/configured ports (collide), port = f(pid) (fragile), system-property-via-Attach (couples discovery to the attach mechanism and is noisy on Windows).

5. **Injection paths — `-javaagent` durable, Attach best-effort; attach protocol implemented natively in Rust (decided).** Both load the same agent. The attach transport is a small PlatynUI platform crate speaking the JVM attach protocol directly (Unix: `.attach_pid<pid>` + `SIGQUIT` + the `/tmp/.java_pid<pid>` socket; Windows: `OpenProcess`/`WriteProcessMemory`/`CreateRemoteThread` invoking `JVM_EnqueueOperation`, reply over a client-created named pipe) — no bundled foreign binary, no JDK required on the test host; the `unsafe` Windows leg gets a focused review. *Rejected alternative — bundling `jattach`:* it would also remove the JDK requirement (it is a standalone C implementation of the same protocol), but it costs a third-party binary per OS × architecture in our wheel, turns failures into exit codes/stderr instead of the structured "attach failed" vs. "agent rejected in target" distinction, and ships an **unsigned foreign** binary whose Windows leg performs `OpenProcess`/`CreateRemoteThread` — an EDR red flag in enterprise environments, where the same operation inside our own signed binary is at least attributable and reviewable. The protocol is small enough (a socket file + signal on Unix, the `JVM_EnqueueOperation` trick on Windows) that owning it beats bundling it; the accepted price is the `unsafe` Windows code and its review. *Ecosystem check (July 2026):* no Rust crate implements the attach **client** — the JVM crates on crates.io (`jni`, `jni-simple`, `j4rs`, `jvmti-bindings`, `robusta_jni`) are JNI/JVMTI bindings for writing a *native agent* or embedding a JVM, i.e. the far side of the wire, while our agent is a Java JAR. So the real choice is own implementation vs. vendoring, not "use a crate". *Middle option, kept as the spike's escape hatch:* jattach is Apache-2.0, so its C sources may be **vendored and statically linked** — no separate binary, inside our own signed artifact — priced at a C toolchain in the build (cross-builds get harder) and foreign `unsafe` we then maintain. Because only the `load` command is needed (jattach implements ten) and only the **Windows** leg is genuinely `unsafe` (Unix is a file + a signal + a socket, all safe), the fallback stays deliberately narrow: if the Windows leg proves worse than expected in the spike, vendor *jattach's Windows leg only* rather than replacing the whole transport. Attach needs no launch change (Java Web Start). Per JEP 451 the Attach+`loadAgent` path warns on JDK 21 and will be default-disallowed in a future release (opt-in `-XX:+EnableDynamicAgentLoading`, settable via `JAVA_TOOL_OPTIONS` without editing the command line). So `-javaagent` is the durable path; Attach is a convenience with a documented expiry. **No JVM listing is needed for any of this** (and JEP 451 does not touch discovery): the "agent present?" signal comes from the handshake file, the "is this PID a JVM?" signal from the classifier's process module check (`jvm.dll` on Windows, `libjvm.so` in `/proc/<pid>/maps` on Linux), and attach itself needs only a PID. Machine-wide JVM enumeration (`jps`-style, via `hsperfdata`) answers a question we never ask — we only care about JVMs that own windows, and those arrive via window enumeration. It is therefore a **non-goal**, also on its merits: `hsperfdata` is off under `-XX:-UsePerfData`, unreliable across containers and user boundaries (`/tmp/hsperfdata_<user>/`), and absent on OpenJ9. If operational need shows up later it belongs in an optional CLI diagnostic, not in the provider path. **Quiescence guarantee:** all of this — handshake-directory scans, JVM discovery, attach — runs only while the agent backend is active (package installed + enabled); with it inactive, the runtime performs no Java-related activity beyond the classifier's passive module check, and the test host never needs a JVM/JDK/`jattach` in any case.

6. **Auto-attach is opt-in.** `providers.java.agent.auto_attach` default **off**: off ⇒ agent used only where the user launched it with `-javaagent`; on ⇒ detected agent-less Swing/JavaFX JVMs are attached automatically (still keyword-free — consent is the one-time config flag, not a per-app call).

7. **Threading: multi-client, EDT-serialized, deadline + generation counter (decided).** The agent accepts **multiple concurrent provider connections** — the Inspector and a test run are separate PlatynUI processes and must not lock each other out. All reads marshal onto the toolkit thread (Swing EDT) anyway, which serializes them naturally; each call runs **with a deadline on the agent side too** — a bare `invokeAndWait` would let a hung EDT pin the RPC handler forever — and abandoned results are discarded, mirroring the JAB pump. The provider treats a hung/degraded agent like JAB treats a frozen JVM (bounded, no runtime hang, `DegradedTracker` discipline). The agent maintains a **UI-generation counter** (bumped on structural toolkit events) published over the reserved notification frame — a cheap invalidation hint for consumers, in v1 informational only.

8. **Native window handle: hybrid (decided).** For the WindowManager delegation of the window patterns, the agent first tries to read the native handle in-process (JDK internals — `sun.awt` peers on 8, their moved/jigsawed forms on 9+; what `--add-opens` that needs per version is spike work); when that fails, the provider falls back to PID + geometry/title matching against the native window list. Exactness when possible, portability always.

9. **Agent build & delivery: own product build, own wheel, entry-point discovery (decided).**

    - **Build:** the agent JAR is a Gradle **product** project (e.g. `java/agent` — deliberately not under `apps/`, which is fixtures), reusing the repo's self-bootstrapping toolchain pattern (checked-in wrapper, Foojay-provisioned JDKs), compiled `-target 8`. `just build-java-agent` builds it; `just build-native` stays JDK-free — a missing JAR surfaces as the provider's actionable diagnostic, not as a build failure. Only the release/wheel recipes make the JAR mandatory.
    - **Delivery:** the JAR ships as its own pure-data wheel **`platynui-provider-java`** (`py3-none-any` — the JAR is platform- and Python-version-neutral, so it is *not* duplicated into the per-platform `platynui-native` wheels, and the native wheel build needs no JDK). Version consistency is enforced by the resolver, not at runtime: the `[java]` extra on `robotframework-platynui` and `platynui-inspector` pins `platynui-provider-java == <same version>` (all packages release in lockstep). **Opt-in-by-install:** the package absent ⇒ Java agent support absent — the provider reports an actionable "install `robotframework-platynui[java]`" diagnostic; consent-by-installation sits *before* the `auto_attach` flag. At runtime a version mismatch aborts (decision 1a) — no compatibility windows.
    - **Discovery = a provider-plugin entry point.** `platynui-provider-java` registers in the entry-point group **`platynui.providers`** (the `importlib.metadata` mechanism pytest/Robot plugins use), exposing in this change exactly `{ agent_jar, version }`. One discovery concept, two transports: **in-process** (the provider lives in the `platynui_native` extension module — under the GIL it asks `importlib.metadata` directly; the normal test-run path, zero configuration) and **co-located-interpreter one-shot** for the Inspector/CLI. The latter is forced by how those wheels work: they use maturin `bindings = "bin"`, so the console script *is* the Rust binary — **there is no Python wrapper process** that could resolve anything. But the binary is installed into the environment's scripts directory *next to that environment's interpreter* (`Scripts\python.exe` / `bin/python`; also true for pipx/uv-tool installs), so it derives the interpreter from its own executable path (fallbacks: `pyvenv.cfg`, `VIRTUAL_ENV`) and runs it **once** with a short `-c` snippet that resolves the `platynui.providers` group via `importlib.metadata` and prints JSON on stdout; the result is cached for the process lifetime. Python runs as a short-lived child process — ABI-agnostic, nothing linked. Embedding libpython was **rejected**: runtime libpython discovery is fragile (Windows venvs lack the DLL, distros split libpython, `cargo run` would need a build Python). Resolution order: explicit config `providers.java.agent.jar` → env var `PLATYNUI_JAVA_AGENT_JAR` (override + the `cargo run` dev leg, wired by the justfile) → entry point (in-process or one-shot) → actionable diagnostic. A `platynui-provider-java agent-path` command prints the JAR path for the operator's `-javaagent:` case.
    - The **general provider-plugin interface** ("providers of arbitrary technologies", dynamically loaded provider libraries, ABI questions) is a separate future proposal; this change only establishes the group name and the metadata shape it will grow from — the same cheap forward-provision as the handshake `toolkits` list.

## Risks / Trade-offs

- [Attach path decays with future JDKs (JEP 451)] → `-javaagent` remains; documented, non-blocking.
- [Auto-attach is instrumentation] → off by default, one-time explicit opt-in, never silent.
- [Cross-platform agent lifecycle (spawn, port, teardown, multiple JVMs)] → the hardest engineering; the spike must exercise multiple concurrent targets.
- [Security: an open agent RPC port] → loopback-only bind **plus** the handshake-file token (any local user can connect to loopback on shared hosts); stale `agent-<pid>` files after a JVM crash must be detected (pid gone ⇒ ignore/clean).
- [Separate delivery package can drift from the provider (multiple venvs, global tools)] → exact `==` pin via the `[java]` extras at install time; at runtime the exact-version handshake aborts with a diagnostic naming both versions — no compatibility windows to reason about.

## Migration Plan

New agent backend + agent artifact; additive on top of `unify-java-provider`. The JAB backend and native providers are unchanged and remain the default floor. Java agent support requires installing `platynui-provider-java` (via the `robotframework-platynui[java]` / `platynui-inspector[java]` extras — opt-in-by-install); enabled via `providers.java.agent.enabled`; full auto behavior only with `auto_attach`. Dev: `just build-native` + `just build-java-agent`. Rollback: disable the agent backend (config) or uninstall the package — everything falls back to JAB/native.

## Spike verification items (approach decided; numbers/mechanics to confirm)

- **Coordinate conversion** (2b): confirm the in-JVM physical-pixel conversion on a HiDPI-scaled monitor across JDK 8 / 17 / 21.
- **Window-handle internals** (8): which `sun.awt`/FX internals expose the native handle per JDK, and the `--add-opens` each needs on 9+ — before the PID+geometry fallback kicks in.
- **Element-model field list** (2): pin the exact attribute/pattern payload against the Swing fixture (the *scope* is "full", the field list is to enumerate).
- **Concurrency** (7): two provider connections (Inspector + test run) against one agent; deadline abandons a wedged EDT job cleanly.
- **Attach protocol** (5): the native Rust attach against a running JVM on each OS, incl. the `unsafe` Windows `CreateRemoteThread` leg and its review.
- **Packaging** (9): agent `-target 8` in the `platynui-provider-java` wheel; entry-point discovery works over both transports (in-process PyO3 lookup in a test run, co-located-interpreter one-shot from the Inspector binary); exact-version handshake aborts on a stale agent with an actionable diagnostic.
