## Context

This is the foundation half of the "agent" side of the Java-toolkit map in [`dev-docs/java-toolkits.md`](../../../dev-docs/java-toolkits.md); the "detection half" is `java-app-classifier` (archived). Everything here is **toolkit-neutral**: getting the agent into a JVM, talking to it, keeping it bounded, shipping it. What a specific toolkit's tree looks like is the adapters' business (`provider-java-swing` first, then `-javafx`/`-swt`).

Captured as **forward design**: transport, discovery, injection and delivery are decided below; the remaining unknowns are consolidated at the end and gated behind the walking skeleton. The verification target is the existing Swing fixture — not because this change is Swing-specific, but because it is the JVM we have.

The consent/fidelity axis is why the agent coexists with the native providers rather than replacing them:

```
              zero consent        one-time consent       per-launch consent
   Fidelity   ├ JAB (Win) ──────────────────────────────────────────────┤
     low      │ AT-SPI (SWT)      │                                       │
              │ AX (Mac)          │      agent (full, all platforms) ─────┤
     high     └───────────────────┴───────────────────────────────────────┘
```

## Goals / Non-Goals

**Goals:**

- An agent that can be put into an **already-running** JVM, on Windows/Linux/macOS, without a JDK on the test host and without changing how the application is launched.
- A transport that is bounded, multi-client, authenticated, and works on Java 8 targets.
- Delivery the user composes: install the package to get Java support, uninstall to remove the capability.

**Non-Goals:**

- Reading any toolkit's tree — that is the adapters. This change surfaces no PlatynUI nodes.
- Instrumentation without consent — the consent is installing `platynui-provider-java`; absent that package nothing attaches.
- A general bytecode-instrumentation framework — the agent reads accessibility/scene models, it does not rewrite app logic.
- Machine-wide JVM enumeration (`jps`/`hsperfdata`-style listing) — only window-owning JVMs are in scope; see decision 5.
- Event push — the wire reserves the frame, v1 uses it only for the generation counter.

## Decisions (proposed) and Open Questions

1. **One PlatynUI agent JAR, both entry points, toolkit self-detection.** A single PlatynUI-owned artifact with `premain` (launch) and `agentmain` (attach) entry points and `toolkit=auto` self-detection — from inside the JVM the active toolkits are unambiguous (a `javax.swing` window hierarchy vs. a JavaFX `Stage` vs. an SWT `Display`), so the agent is the authoritative classifier that host-side detection defers to. Self-detection reports the **set** of active toolkits; a JVM running several at once is the deferred mixed-toolkit case. The attach driver (a small main class around `VirtualMachine.attach`/`loadAgent`) ships **inside the agent JAR** — no separate attacher artifact — and reports "attach failed" and "agent rejected inside the target" (e.g. a sandboxed-JNLP `SecurityManager`) as distinct exit codes so failures stay diagnosable. That driver is only the convenience path for hosts that happen to have a JDK (`VirtualMachine` lives in `jdk.attach`); hosts without one are served by the native transport of decision 5, so **no foreign attacher binary is bundled**.

1a. **Control plane / data plane split; data plane = loopback TCP + handshake file.** Injection (`-javaagent` or Attach) is a **one-time control plane**; the running traffic flows over the agent's **own data plane**. The two must not be conflated — the JDK's attach mechanism is a command channel only (`load`, `properties`, dumps; short-lived sessions, one listener thread), and on Windows every attach is an `OpenProcess`+`CreateRemoteThread` into the target (EDR-visible), so it is used exactly once to load the agent and never for reads. (Prior art contrast: JAB *fuses* control and data into Win32 messaging — hidden-window rendezvous, then synchronous `SendMessage`/`WM_COPYDATA`/shared memory — which is why it is zero-config but Windows-only, blocks callers on a hung JVM, and needs UIPI workarounds. We keep its good idea, zero-config rendezvous, in portable form.)

    - **Transport:** the agent binds `127.0.0.1:0` (OS-chosen ephemeral port) with a plain `ServerSocket`. This is forced, not merely chosen: the agent must run on **Java 8** targets, where Unix domain sockets don't exist yet (JEP 380 = Java 16) and a named-pipe *server* is impossible in pure Java — loopback TCP is the only all-platform Java-8 server option. Framing: newline-delimited JSON-RPC 2.0; short client-side per-call timeouts, never open-ended socket reads. A **server-initiated notification frame** (a message without an `id`) is part of the wire from day one — v1 uses it only to publish the UI-generation counter (decision 7), so later `event_capabilities` need no protocol break. The handshake enforces an **exact provider↔agent version match** (decided): agents cannot be unloaded, so a mismatch simply **aborts** the connection with a diagnostic naming both versions and the fix (restart the JVM with the current agent) — simplest rule, no silent drift, and no semver-compatibility windows planned; delivery keeps versions aligned at install time instead (decision 9's exact pin).
    - **Handshake file (rendezvous + auth + discovery in one):** on startup the agent writes `<per-user runtime dir>/platynui/agent-<pid>` in an **owner-only directory** containing `{ port, token, toolkits, agentVersion, pid }`, and deletes it on shutdown. "Owner-only" is POSIX `0700` on Unix and an **ACL restricted to the current user** on Windows — the latter is not a detail to leave implicit, since Windows is the primary platform and a default-inherited ACL would expose the token to every local account. `toolkits` is a **list** from day one, so a later mixed-toolkit proposal needs no handshake-format break. The provider discovers agents by reading these files and must present the random `token` in the connection handshake. This one mechanism solves: port collisions (the OS picks), discovery for **user-launched** `-javaagent` targets (no port argument needed; works even with `-XX:+DisableAttachMechanism`), authentication on multi-user hosts (loopback TCP alone is connectable by any local user — terminal servers are common in enterprise Java), and the classifier's "agent present in this JVM?" signal (file exists + ping). The token is deliberately **not** passed as a `-javaagent` argument (`/proc/<pid>/cmdline` is world-readable on Linux); the agent generates it and only the `0700` file carries it.

2. **Element identity: agent-assigned registry ids backed by weak references (decided).** Every element the agent hands out carries an id from an agent-side registry holding **weak** references — not Java `identityHashCode` (collision-prone, reused after GC) and not strong-ref caches (which would leak every component ever touched). The registry also backs a cheap **liveness endpoint**: an id is live while it still resolves to an object that is still attached to a showing window. This is what lets an adapter answer `UiNode::is_valid` honestly, which consumers rely on (the Robot Framework library keeps a scoped root's element exactly as long as it reports valid).

3. **Coordinates: the agent emits physical desktop pixels (decided).** The conversion happens in the JVM, where the toolkit's own scaling knowledge lives, so the wire carries one unambiguous space and the provider stays dumb — no provider-side calibration heuristic (the inverse of what JAB forced on us). *How* a given toolkit converts is the adapter's business (Swing/AWT via `GraphicsConfiguration`, FX via glass/`Screen`); this decision fixes only the contract.

4. **Port / instance discovery — the handshake file (decision 1a).** The agent binds an OS-chosen port and publishes it with the auth token in the per-user `agent-<pid>` file; the client discovers agents by scanning that directory. No port arguments, no collisions across concurrent target JVMs, no repeated attach round-trips just to read a system property (which on Windows would mean a fresh `CreateRemoteThread` per poll). *Rejected alternatives:* fixed/configured ports (collide), port = f(pid) (fragile), system-property-via-Attach (couples discovery to the attach mechanism and is noisy on Windows).

5. **Injection paths — Attach primary, `-javaagent` durable fallback; attach protocol implemented natively in Rust (decided).** Both load the same agent. The attach transport is a small PlatynUI crate speaking the JVM attach protocol directly (Unix: `.attach_pid<pid>` + `SIGQUIT` + the `/tmp/.java_pid<pid>` socket; Windows: `OpenProcess`/`WriteProcessMemory`/`CreateRemoteThread` invoking `JVM_EnqueueOperation`, reply over a client-created named pipe) — no bundled foreign binary, no JDK required on the test host; the `unsafe` Windows leg gets a focused review.

    *Rejected alternative — bundling `jattach`:* it would also remove the JDK requirement (it is a standalone C implementation of the same protocol), but it costs a third-party binary per OS × architecture in our wheel, turns failures into exit codes/stderr instead of the structured "attach failed" vs. "agent rejected in target" distinction, and ships an **unsigned foreign** binary whose Windows leg performs `OpenProcess`/`CreateRemoteThread` — an EDR red flag in enterprise environments, where the same operation inside our own signed binary is at least attributable and reviewable. *Ecosystem check (July 2026):* no Rust crate implements the attach **client** — the JVM crates on crates.io (`jni`, `jni-simple`, `j4rs`, `jvmti-bindings`, `robusta_jni`) are JNI/JVMTI bindings for writing a *native agent* or embedding a JVM, i.e. the far side of the wire, while our agent is a Java JAR. So the real choice is own implementation vs. vendoring. *Middle option, kept as the walking skeleton's escape hatch:* jattach is Apache-2.0, so its C sources may be **vendored and statically linked** — no separate binary, inside our own signed artifact — priced at a C toolchain in the build (cross-builds get harder) and foreign `unsafe` we then maintain. Because only the `load` command is needed (jattach implements ten) and only the **Windows** leg is genuinely `unsafe` (Unix is a file + a signal + a socket, all safe), the fallback stays deliberately narrow: if the Windows leg proves worse than expected, vendor *jattach's Windows leg only* rather than replacing the whole transport.

    **Attach is the primary path, not a convenience.** Java applications are launched by scripts, installers or Web Start — the launch line is typically not PlatynUI's to change — and the Inspector's core use is looking into an application that is *already running*, where `-javaagent` is impossible by definition. `-javaagent` is therefore the **durable fallback**: for hosts where attach is blocked, and for the day the JEP 451 sunset arrives (the path warns on JDK 21 and will be default-disallowed in a future release; `-XX:+EnableDynamicAgentLoading` restores it, settable via `JAVA_TOOL_OPTIONS` without editing the command line — which the walking skeleton must confirm, since "we do not touch how the app starts" depends on it). That ordering puts the `unsafe` Windows leg on the critical path, which is why its review and the narrow jattach fallback matter more, not less.

    **No JVM listing is needed for any of this** (and JEP 451 does not touch discovery): the "agent present?" signal comes from the handshake file, the "is this PID a JVM?" signal from the classifier's process module check (`jvm.dll` on Windows, `libjvm.so` in `/proc/<pid>/maps` on Linux), and attach itself needs only a PID. Machine-wide enumeration (`jps`-style, via `hsperfdata`) answers a question we never ask — we only care about JVMs that own windows, and those arrive via window enumeration. It is a **non-goal**, also on its merits: `hsperfdata` is off under `-XX:-UsePerfData`, unreliable across containers and user boundaries, and absent on OpenJ9.

6. **Injection policy: automatic by default, and the consent is the installation (decided).** The deliberate act is installing `platynui-provider-java` (decision 9) — nobody gets in-JVM instrumentation without having asked for Java support, and uninstalling removes the capability entirely. On top of that, attaching to a detected agent-less JVM happens **automatically**: a flag defaulting to `off` would switch the feature off for its own primary use case (decision 5: attach *is* the normal path), and a test run that silently declines to attach is the same trap as an empty Inspector. An environment that wants instrumentation only where the operator launched with `-javaagent` can still turn it off.

    *Ownership:* this change owns the **mechanism** and the gate that makes it available at all (`providers.java.agent.enabled`, plus `providers.java.agent.jar` for discovery overrides). The **`auto_attach` flag itself lives with the consumer** — deciding "this window's JVM has no agent, attach to it" needs window detection and the router, which are `provider-java-swing`. Stated here because the policy belongs with injection; implemented there because that is where it can be observed.

7. **Threading: multi-client, toolkit-thread-serialized, deadline + generation counter (decided).** The agent accepts **multiple concurrent client connections** — the Inspector and a test run are separate PlatynUI processes and must not lock each other out. All reads marshal onto the toolkit thread anyway, which serializes them naturally; each call runs **with a deadline on the agent side too** — a bare `invokeAndWait` would let a hung toolkit thread pin the RPC handler forever — and abandoned results are discarded, mirroring the JAB pump. Clients treat a hung/degraded agent like JAB treats a frozen JVM (bounded, no runtime hang). The agent maintains a **UI-generation counter** (bumped on structural toolkit events) published over the reserved notification frame — a cheap invalidation hint, in v1 informational only; per-element liveness is answered by decision 2's endpoint, not by this counter.

8. **Quiescence.** With the agent backend inactive (package absent, or `providers.java.agent.enabled` false), nothing Java-related runs: no handshake-directory scanning, no attach, no agent JAR resolution. The test host never needs a JVM, JDK or `jattach` in any case — the attach transport is native and only ever talks to the target application's own JVM.

9. **Build & delivery: own product build, own wheel, entry-point discovery (decided).**

    - **Build:** the agent JAR is a Gradle **product** project (`java/agent` — deliberately not under `apps/`, which is fixtures), reusing the repo's self-bootstrapping toolchain pattern (checked-in wrapper, Foojay-provisioned JDKs), compiled `-target 8`. `just build-java-agent` builds it; `just build-native` stays JDK-free — a missing JAR surfaces as an actionable diagnostic, not a build failure. Only the release/wheel recipes make the JAR mandatory.
    - **Delivery:** the JAR ships as its own pure-data wheel **`platynui-provider-java`** (`py3-none-any` — the JAR is platform- and Python-version-neutral, so it is *not* duplicated into the per-platform `platynui-native` wheels, and the native wheel build needs no JDK). Version consistency is enforced by the resolver, not at runtime: the `[java]` extra on `robotframework-platynui` and `platynui-inspector` pins `platynui-provider-java == <same version>` (all packages release in lockstep). **Opt-in-by-install:** the package absent ⇒ Java agent support absent, with an actionable diagnostic; consent-by-installation sits *before* the `auto_attach` flag.
    - **Discovery = a provider-plugin entry point.** `platynui-provider-java` registers in the entry-point group **`platynui.providers`** (the `importlib.metadata` mechanism pytest/Robot plugins use), exposing `{ agent_jar, version }`. One discovery concept, two transports: **in-process** (the provider lives in the `platynui_native` extension module — under the GIL it asks `importlib.metadata` directly; the normal test-run path, zero configuration) and **co-located-interpreter one-shot** for the Inspector/CLI, which are maturin `bindings = "bin"` console scripts with **no Python wrapper process**: the binary derives the environment interpreter from its own executable path (fallbacks: `pyvenv.cfg`, `VIRTUAL_ENV`) and runs it once with a short `-c` snippet that prints the resolved manifest as JSON, cached for the process lifetime. Embedding libpython was **rejected**: maturin ignores `abi3` for `bindings = "bin"` and builds one wheel per Python version, because a binary links a concrete libpython at build time — the Inspector/CLI wheels are version-independent today and would stop being so. Resolution order: explicit config `providers.java.agent.jar` → env var `PLATYNUI_JAVA_AGENT_JAR` (override + the `cargo run` dev leg) → entry point → actionable diagnostic. A `platynui-provider-java agent-path` command prints the JAR path for the operator's `-javaagent:` case.
    - The **general provider-plugin interface** (dynamically loaded providers, ABI questions — see [`dev-docs/provider-plugins.md`](../../../dev-docs/provider-plugins.md)) is separate future work; this change only establishes the group name and the metadata shape it will grow from.

## Risks / Trade-offs

- [Attach path decays with future JDKs (JEP 451)] → `-javaagent` remains as the durable fallback; the `EnableDynamicAgentLoading` opt-in is settable per environment, documented, non-blocking.
- [Auto-attach is instrumentation, and on by default] → gated by an explicit install, never present in a default installation; `auto_attach=off` remains; the JVM's own JEP 451 warning makes a dynamic load visible in the target's log.
- [The `unsafe` Windows attach leg is on the critical path] → focused review, plus the narrow escape hatch of vendoring jattach's Windows leg.
- [Cross-platform agent lifecycle (spawn, port, teardown, multiple JVMs)] → the hardest engineering; the walking skeleton must exercise multiple concurrent targets.
- [Security: an open agent RPC port] → loopback-only bind **plus** the handshake-file token (any local user can connect to loopback on shared hosts); stale `agent-<pid>` files after a JVM crash must be detected (pid gone ⇒ ignore/clean).
- [Separate delivery package can drift] → exact `==` pin via the `[java]` extras at install time; at runtime the exact-version handshake aborts with a diagnostic naming both versions.

## Verification items (approach decided; mechanics to confirm)

- **Attach protocol** (5): the native Rust attach against a running JVM on each OS, incl. the `unsafe` Windows `CreateRemoteThread` leg and its review; and whether `-XX:+EnableDynamicAgentLoading` via `JAVA_TOOL_OPTIONS` works without touching the launch command.
- **Concurrency** (7): two client connections (Inspector + test run) against one agent; the deadline abandons a wedged toolkit-thread job cleanly.
- **Multiple targets** (1a): handshake-file discovery across two concurrent JVMs — distinct ports/tokens, correct PID mapping, stale-file cleanup after a killed JVM.
- **Packaging** (9): agent `-target 8` in the wheel; discovery over both transports; the exact-version handshake refuses a stale agent with an actionable diagnostic.
