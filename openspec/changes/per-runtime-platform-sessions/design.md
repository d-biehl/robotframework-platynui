## Context

The runtime already owns its **providers** but borrows its **platform**. Providers are built per runtime by a factory — `AtspiFactory::create()` returns `Arc::new(AtspiProvider::new())`, and each provider holds its connection in an instance field: `conn: ClearableCell<Arc<AccessibilityConnection>>` plus an `is_shutdown: AtomicBool` (`provider-atspi/src/lib.rs`). `ClearableCell` is a const-initializable `Mutex<Option<T>>` that re-resolves after `clear()` (`provider-atspi/src/clearable_cell.rs`; its tests `get_or_init_after_clear` and `get_or_try_init_err` prove re-init and non-poisoning). Because each runtime gets a fresh instance, providers never leak state across runtimes.

The platform layer is the opposite. Devices are `inventory`-registered `&'static` singletons (`register_pointer_device!`, `register_platform_module!`, etc. in `crates/core/src/platform/`), and connection state lives in process-global statics gated by a reference-counted lease:

- `PlatformModulesLease` / `PLATFORM_MODULES_STATE` runs every module's `initialize()` when `active_runtimes` goes 0→1 and every `shutdown()` at 1→0 (`crates/runtime/src/runtime/platform_modules.rs:29-78`). The `Runtime` stores platform devices as `Option<&'static dyn PointerDevice>` etc. (`runtime/mod.rs:43-54`) and holds the lease in `platform_guard`.
- X11's connection is `static X11: OnceLock<Mutex<Option<X11Handle>>>`; `connection()` connects inside `get_or_init` (fires once per process), and `shutdown_connection()` does `guard.take()` (`platform-linux-x11/src/x11util.rs:16-82`). After the first teardown the `OnceLock` stays initialized but empty, so the connect closure never re-runs → `x11 connection: not available after shutdown or failed connect`.
- The same `OnceLock` + `.take()` defect exists in the X11 highlight controller (`platform-linux-x11/src/highlight.rs:33,48`) and the Windows highlight controller (`platform-windows/src/highlight.rs:66`).
- The `platform-linux` mediator resolves X11 vs Wayland once into a `static RESOLVED: Mutex<Option<Resolved>>` and routes every device call through it (`platform-linux/src/lib.rs:67-128`).

`BareMetal` is `scope='SUITE'` and builds one native `Runtime` per suite via a `@cached_property` (`src/PlatynUI/BareMetal/__init__.py:238,787-818`); `Runtime::drop → shutdown() → platform_guard.release()` (`runtime/mod.rs:249-268`). So a multi-suite run drops the lease to zero between suites, tears the X11 connection down, and cannot rebuild it — confirmed: 16/26 tests fail in `just test-acceptance-x11`. Session identity is currently carried by the **process environment** (`startxsession.sh` gives each session its own `XDG_RUNTIME_DIR` + `dbus-run-session`, deriving `DISPLAY` / `AT_SPI_BUS_ADDRESS` per wrapper process), which is why two sessions in one process are impossible today.

## Goals / Non-Goals

**Goals**
- Each runtime owns its platform instances and releases them on drop, sharing no connection or mutable global with any other runtime.
- The X11 multi-suite acceptance lane passes by construction; the X11 and Windows highlight bugs are fixed by removing the offending globals.
- A construction-time `config` dictionary binds a runtime to a specific session (platform display + accessibility bus), threaded into both platform and provider factories, with an absent/empty `config` reproducing today's behavior exactly.
- Establish the `PlatformFactory` shape that Wayland, Windows, and macOS will adopt in later phases.

**Non-Goals**
- Internalizing Wayland's process-global state (`connection.rs` `GLOBAL` + event thread, `input::BACKEND`, `desktop::OUTPUTS`, `platynui_ipc` window map). In Phase 1 the Wayland factory wraps the existing globals.
- Actually running two sessions (X11 + Wayland) concurrently in one process — depends on the Wayland work above.
- Flipping `PlatynUI` from `scope='GLOBAL'` to `scope='SUITE'` and reconciling `src/PlatynUI/core/runtime.py`'s `_RuntimeAccessor` singleton.
- Windows UIA (`thread_local` COM apartment) and macOS AX (main-thread) adopting the per-runtime shape. Phase 1 only removes the Windows highlight global.

## Decisions

**D1 — `PlatformFactory` mirrors `UiTreeProviderFactory`.** Add a trait with `id() -> &'static str`, `can_serve(&RuntimeConfig) -> bool`, and `create(&RuntimeConfig) -> Result<PlatformBundle, PlatformError>`, registered by `inventory` like provider factories. A factory is handed the whole `RuntimeConfig` and reads its own slice by `self.id()` (so `can_serve` can also see the `platform.backend` selector). `PlatformBundle` is an owned struct of `Arc<dyn PointerDevice>`, `Arc<dyn KeyboardDevice>`, `Arc<dyn ScreenshotProvider>`, `Arc<dyn HighlightProvider>`, `Arc<dyn WindowManager>`, `Arc<dyn DesktopInfoProvider>`. The `Runtime` stores the bundle by value instead of `Option<&'static dyn …>` (`runtime/mod.rs:43-54`), and resolves the active factory by `can_serve` (or an explicit `platform.backend`). (Implementation note: the fields are `Arc`, not the `Box` originally sketched — see D2; the pointer device must also be held by the runtime's `PointerEngine`, and an `Arc` clone avoids a self-referential borrow on the `Runtime`.) _Alternative considered:_ keep the `&'static` device singletons but make each connection a clearable cell (the narrow memory fix). Rejected: it fixes only sequential reconnection, not ownership, isolation, or config-bound sessions, and leaves the lease/global architecture in place.

**D2 — Devices share the connection via `Arc`, not stored borrows.** Each device owns an `Arc` clone of an owned connection struct (`Arc<X11Connection>` holding the `RustConnection`, root, keymap, atoms). This is the `provider-atspi` pattern (`Arc<AccessibilityConnection>`) generalized to the whole device set. It sidesteps the self-referential-struct problem: the `Runtime` cannot hold both a `Connection` field and `&that_field`, but it *can* hold owned devices that each hold an `Arc`. Bundle drop → devices drop → last `Arc` closes the FD; the highlight overlay thread is signalled and joined in the highlight device's `Drop`. The same reasoning forces the bundle's trait objects to be `Arc<dyn …>` rather than `Box`: the runtime's `PointerEngine` currently borrows a `&'static dyn PointerDevice` (`runtime/mod.rs:48`, `pointer.rs:269`), and once the device is owned per-runtime the engine must hold an `Arc<dyn PointerDevice>` clone instead of borrowing from a sibling field. _Alternative:_ a `PlatformSession` object handing out `&dyn Device` borrows per call. Rejected: extra indirection for no benefit over `Arc`, and still needs the session to own the devices anyway.

**D3 — Delete `PlatformModulesLease`; ownership is the lifecycle.** With per-runtime bundles there is no shared global to reference-count. `Runtime::new` calls the chosen factory's `create()`; `Runtime::drop` drops the bundle. `create()` must roll back partially-constructed devices on failure (the lease's `initialized_modules` rollback at `platform_modules.rs:39-42` moves into the factory). This removes `PLATFORM_MODULES_STATE`, `platform_guard`, and the `platform_overrides_require_global_modules` machinery.

**D4 — `RuntimeConfig`: two buckets, id-keyed, config > env > auto-detect.** The native `Runtime(config)` parses the dict into `RuntimeConfig { platform: Section, providers: Section }`. The `platform` section holds an optional reserved `backend` selector plus a per-id sub-map for each platform backend; the `providers` section holds a per-id sub-map for each provider. Each factory, handed the `RuntimeConfig`, reads its own sub-map by `self.id()` (`config.platform[self.id()]`, `config.providers[self.id()]`) and never another component's. Every backend resolves each setting as `config value → env var → auto-detect` (so `x11util::connect_raw` and `connect_a11y_bus` gain a config-value path in front of their `env::var` reads). Absent buckets/keys ⇒ all-env ⇒ current behavior. Unclaimed buckets, ids, or keys are ignored with a `tracing::debug!` (portability + forward-compat; typos fail silent — accepted). _Alternative shapes considered and rejected:_ flat dotted keys (no natural grouping, awkward to pass a whole backend's block); a single fixed typed config struct (not open-ended, breaks the cross-platform "carry every OS's keys in one dict" goal).

**D5 — Config value representation crosses PyO3 as a loosely-typed map.** The Python side is a nested `dict` (`{'platform': {'backend': 'x11', 'x11': {'display': ':1'}}, 'providers': {'atspi': {'bus_address': …}}}`) — note the buckets mix a reserved scalar key (`backend`) with id-keyed sub-maps, so the leaf value type is open, not a uniform three-level dict. On the Rust side each leaf value is a small owned enum (string / int / bool / float / nested), converted once at construction. Backends read typed accessors (`get_str("display")`, `get_str("bus_address")`) and ignore/warn on type mismatch. No serde schema is imposed on the open sub-maps, matching the tolerant-resolution decision.

**D6 — The `platform-linux` mediator becomes a `PlatformFactory`.** Instead of a `PlatformModule` that fills a `static RESOLVED`, it is a factory whose `can_serve`/`create` pick X11 vs Wayland from `config.platform.backend` (or env auto-detect) and build the corresponding backend's `PlatformBundle`. In Phase 1 the X11 branch is fully per-instance; the Wayland branch's `create()` drives the existing `connection::set_global_and_start` / `clear_global` globals and its `Drop` clears them — correct for one-Wayland-runtime-at-a-time, deferring true per-instance Wayland (D-Non-Goal).

**D7 — `use_mock` becomes sugar for `config={'platform': {'backend': 'mock'}}`.** The mock platform + mock provider are selected through the same config path; `BareMetal(use_mock=True)` and `Runtime.new_with_mock()` are kept as thin conveniences that set that backend, so existing call sites are unaffected. _Alternative:_ remove `use_mock`. Rejected as needless churn for tests.

**D8 — `config` is a separate `BareMetal` argument, construction-time only.** It sits beside the unchanged scoped behavioral dicts (`query_settings`, `pointer_profile`, `keyboard_profile`) and is consumed once in `_create_runtime()`. There is no scoped/per-call override and no re-bind keyword, because a live connection cannot be re-pointed at a new display (spec `runtime-session-config` / "fixed at construction").

## Risks / Trade-offs

- **Wayland stays global-backed in Phase 1** → a second concurrent Wayland (or X11+Wayland) runtime would collide on `GLOBAL`/`BACKEND`/`OUTPUTS`. Mitigation: explicit non-goal; the factory wraps the existing globals, which are already correct for the sequential one-at-a-time case; concurrency waits for the internalization phase.
- **`inventory`-`&'static`-device → factory conversion touches every `platform-*` crate** and the core registration macros (internal BREAKING). Mitigation: mechanical and compile-enforced; keep cross-platform crates green with `just check-windows` / `just clippy-windows`; no external consumers of these APIs.
- **AT-SPI is display-coupled** — `AccessibilityConnection::new()` discovers the bus from the current `DISPLAY`'s root window, so a config-bound X11 session needs its bus passed explicitly. Mitigation: `providers.atspi.bus_address` (D4); the test harness already emits per-session buses (`bus_$DISPLAY`).
- **Removing the lease loses its partial-init rollback** unless `create()` reproduces it. Mitigation: D3 moves the rollback into the factory; a device that fails to build tears down the ones already built before returning the error.
- **Other crates build runtimes** — `crates/cli` (`lib.rs:144`), `crates/playground` (`main.rs:10`), `apps/inspector` (`lib.rs:834`) via `Runtime::new()`, and `crates/cli/src/test_support.rs` + the native mock path via `new_with_factories_and_platforms`/`PlatformOverrides`. Mitigation: keep `Runtime::new()` no-arg (empty config) so the read-only consumers are untouched; rework the factories-and-platforms path in the same change and let `just check` / `just test` catch any compile breakage across the workspace.
- **Windows/macOS thread affinity** (COM apartment / main-thread AX) must not be designed out. Mitigation: `PlatformFactory::create` returns an owned bundle without prescribing the thread it runs on, so a later Windows/macOS backend may spin up its own thread; Phase 1 does not force a model on them.
- **Silent typos** from tolerant resolution. Mitigation: accepted by decision; the debug log and the Inspector's effective-config view make the applied settings observable.
- **Native rebuild required.** Mitigation: standard — `just build-native` / `just test-python`; noted in the migration plan and tasks.

## Migration Plan

Behavioral at the Rust platform layer, **additive** at the public RF/Python surface (new `config=` defaulting to current behavior). Requires a native rebuild (`maturin`), so Python/RF work sequences after the binding rebuild. Steps: (1) core `PlatformFactory` + `RuntimeConfig` + registration; (2) X11 backend per-instance ownership (connection/keymap/atoms/highlight → `Arc`); (3) mediator-as-factory, Wayland branch wrapping existing globals; (4) delete lease + globals; (5) `Runtime(config)` in PyO3 + `.pyi`; (6) `BareMetal config=`; (7) docs; (8) verify via `just test` + `just test-python` + the `just test-acceptance-x11` multi-suite lane (real provider). Rollback: revert the change — there is no persisted state, migration, or data-model change; the environment-derived default path is unchanged behavior.

## Open Questions

- **Argument / key names:** `config=` vs `runtime_config=`; the force-selector `platform.backend` vs `platform.use`. Cosmetic; settle during implementation.
- **Provider *selection* vs configuration:** Phase 1 keeps provider selection automatic (all discovered, per platform) and uses `providers.<id>` only for settings. Should `config` also be able to restrict which providers are active? Deferred unless a concrete need appears.
- **Config value type:** a bespoke small enum vs reusing an existing value type (e.g. a `serde_json::Value`) for the open leaf maps. Lean bespoke to avoid a new dependency in `core`; confirm during implementation.
- **How `PlatynUI` (the future high-level library) shares the same `config` plumbing** once it moves to `scope='SUITE'` — noted for the follow-up phase, not decided here.
