# Design

## Context

See proposal.md for why the site exists and specs/user-docs-site/spec.md for what it must do. The facts that shape the approach:

- **`docs/` is reserved for user documentation** (`docs/README.md`, CONTRIBUTING.md §11). Today it holds `README.md`, `talks/robocon_2025.md` and a `.gitignore` for a generated `xpath/` folder.
- **The repository currently lives at `github.com/d-biehl/robotframework-platynui`,** while the package metadata and CONTRIBUTING.md already link to its original home, `github.com/imbus/robotframework-PlatynUI` (`pyproject.toml` `[project.urls]`, CONTRIBUTING.md §11). The GitHub Pages address therefore changes when the repository moves back: owner, host and base path all differ.
- **CI is one workflow, `.github/workflows/ci.yml`,** with `permissions: contents: read` at the top. It runs on pushes and pull requests to `main` and `new_core`. The real-provider acceptance lanes run there as the `acceptance-linux` job (`just test-acceptance-x11` / `-compositor`). The Windows lane runs locally (`just test-acceptance-windows`).
- **The acceptance lanes are RobotCode profiles in `robot.toml`:**
  - `real` selects `acceptance AND real`.
  - `real-x11`, `real-wayland` and `real-windows` exclude the other platforms' tags, and the Linux ones bring their session through `wrapper`.
  - `paths = "tests"`; profiles select by tags and never reshape `paths` (comment in `robot.toml`).
  - A path passed on the command line runs a different tree under the same profile and session.
- **Starlight conventions:**
  - Pages live in `src/content/docs/`, and `src/content.config.ts` declares the `docs` collection with Starlight's `docsLoader` and `docsSchema`.
  - The sidebar is configured in `astro.config.mjs`, with explicit groups whose items can be autogenerated from a directory (sorted by file name unless pages set `sidebar.order`).
  - Code blocks go through Expressive Code; extra TextMate grammars are added through `expressiveCode.shiki.langs`.
  - Broken-link checking is the community plugin `starlight-links-validator`, which Starlight's own site uses.
- **The GitHub Pages recipe for Astro** builds the site, uploads it as a Pages artifact, and deploys it in a separate job that holds `pages: write` and `id-token: write`. Astro takes the public URL as `site` and the sub-path as `base`.
- **Keyword docs** are the docstrings in `src/PlatynUI/BareMetal/__init__.py` (`doc_format='ROBOT'`), which the maintainer treats as the contract. A Markdown generator for Robot Framework library documentation is being built in RobotCode and will produce the reference later.
- **The demo application** (`add-demo-app`) is the target every example drives. It is started with `platynui-demo` and found through the launch recipe its spec defines.

## Goals / Non-Goals

**Goals:**
- A site frame that content can grow into page by page, without revisiting structure, tooling or deployment.
- Examples that cannot go stale, because the page shows the very file a test lane runs.
- No coupling to the repository's current address.
- Node.js stays a docs-only tool.

**Non-Goals:**
- Writing the bulk of the content. Concepts, guides, tools and troubleshooting follow in later changes or commits.
- Generating the keyword reference, which belongs to the RobotCode generator change.
- Translations (Starlight's i18n stays unused for now), versioned docs, a custom domain, and site search tuning beyond Starlight's built-in search.

## Decisions

### 1. Astro + Starlight in `docs/`, npm, standard layout

- **The Astro project root is `docs/`:**
  - `astro.config.mjs`, `package.json` and `package-lock.json`;
  - `src/content.config.ts`;
  - pages under `src/content/docs/<section>/`;
  - images under `src/assets/`;
  - static files under `public/`.
- **`docs/talks/` stays where it is.** It is not under `src/content/docs/` and therefore not part of the site.
- **`docs/.gitignore`** gains `node_modules/`, `dist/` and `.astro/`.
- **npm** is used because it ships with Node.js and needs no extra tool; the lockfile pins the dependency tree. The Node.js version is pinned in `docs/.nvmrc` to the current LTS line, and CI reads it from there.

Alternatives considered: pnpm (one more tool for contributors), and a separate repository for the site (it would lose the "examples are the files the lanes run" property).

### 2. Sections are fixed in the configuration and hidden while empty

- **`astro.config.mjs` lists the six sections in order**, each as a group autogenerated from its directory: `getting-started/`, `concepts/`, `guides/`, `tools/`, `reference/`, `troubleshooting/`.
- **Empty sections are skipped:** the configuration checks each directory for at least one page and leaves out groups without pages. That keeps "a section without pages does not appear" out of the content's hands and lets the Reference section appear by itself once the generator writes pages into `reference/`.
- **Order within a section** comes from `sidebar.order` in each page's frontmatter, not from file names.

### 3. RobotCode's grammar for highlighting

- **The grammar file** `robotframework.tmLanguage.json` from RobotCode's repository is vendored as `docs/grammars/robotframework.tmLanguage.json`, together with RobotCode's license notice and the source commit it was taken from.
- **Registration:** `expressiveCode.shiki.langs` loads it, with the aliases `robotframework` and `robot`.
- **Updates are a manual copy** with the new commit noted. RobotCode is Apache-2.0, like this project, and maintained by the same author.

### 4. Link checking on every build

- **`starlight-links-validator` runs on every build,** not only behind an environment flag. A broken link or anchor fails `astro build`, and with it the `just` recipe and CI.
- **Link form:** with a base path, Markdown links are not rewritten by Astro, so the form in which pages link to each other must work both locally (base `/`) and under a repository base path. The first implementation task builds a probe page under both and settles the form, relative links or the validator's base-aware absolute form. The writing rules then state it.

### 5. URL and base from the environment

- **`astro.config.mjs` reads `site` and `base`** from the environment variables `PLATYNUI_DOCS_SITE` and `PLATYNUI_DOCS_BASE`. When they are absent, `site` is unset and `base` is `/`, which is the local case.
- **In CI, `actions/configure-pages`** reports the repository's Pages `origin` and `base_path`, and the build step passes them on.
- **The result:** the configuration names no owner, repository or host, so moving the repository back needs no change in the repository, only the Pages setting on the new home.

### 6. Examples are files, included through `?raw`

- **Each example is a runnable suite** in `docs/examples/<topic>/<name>.robot`.
  - It is complete on its own: `*** Settings ***` with its library imports, setup and teardown included, and no shared resource file that would hide steps a reader needs.
  - It starts the demo application with the documented launch recipe, and ends it through its own UI.
- **An MDX page includes an example** with `import source from '…/examples/…/name.robot?raw'` and Starlight's `<Code code={source} lang="robotframework" title="name.robot" />`. Since `docs/examples/` is inside the Astro project, Vite reads it without extra file-system permissions.
- **The example suites carry the tags `acceptance` and `real`** with no platform tag, so the existing lane profiles select them.
- **They run as a separate tree:** `robotcode --profile real-x11 run docs/examples` and the matching Wayland and Windows forms. This keeps `paths = "tests"` and the suite names of the main tree unchanged.
  - A recipe `just test-docs-examples` runs them on the current OS's lanes.
  - The `acceptance-linux` job gains a step that runs them, once `add-demo-app` provides the demo command to the lane sessions.

Alternatives considered: examples under `tests/` (outside the Astro project, and they would mix teaching material into the regression tree), and code copied into the pages with a separate check (it can drift).

### 7. A separate docs workflow

- **`.github/workflows/docs.yml`** has two jobs.
  - **`build`** runs on pull requests and pushes. It checks out the repository, sets up Node from `docs/.nvmrc` with the npm cache, runs `actions/configure-pages`, `npm ci` and `npm run build` in `docs/` with the derived address in the environment, and uploads `docs/dist` with `actions/upload-pages-artifact`.
  - **`deploy`** runs only for pushes to `main`. It needs `build`, holds `pages: write` and `id-token: write` in the `github-pages` environment, and runs `actions/deploy-pages`.
- **Why a separate file:** the publishing permissions stay out of `ci.yml`, whose permissions stay `contents: read`, and a docs-only change does not wait for the Rust and Python jobs.
- **For a pull request** `actions/configure-pages` can only report the address when Pages is enabled. Without it the build falls back to the local root.

### 8. Writing rules live in `dev-docs/user-docs.md`

The rules a contributor follows when writing the site live in one developer document, English and normative.

- **Audience:**
  - Robot Framework users, addressed as "you".
  - Robot Framework terms (keyword, suite, variable, scope).
  - No Rust, providers or accessibility-API internals outside the pages about installation, platforms and troubleshooting.
- **The four page types and their outline:**
  - tutorial: a guided path through one working example;
  - guide: goal, prerequisites, a complete example, variations, pitfalls;
  - concept: why it matters, the idea, examples of increasing size, common mistakes;
  - reference: generated, never written by hand.
- **Examples:**
  - The first appearance of a topic is complete; later snippets are focused.
  - Current Robot Framework syntax (`VAR`, `IF`, `FOR`) and the conventions of the `robot-test-style` skill.
  - `@Id` before `@Name`.
  - Platform- and toolkit-neutral locators (`(Window|Frame)`, `*`), because roles depend on platform and toolkit.
  - Show the failure output where it teaches something.
- **Content rules:**
  - No status or roadmap text, except one preview notice on the landing page.
  - One home per fact.
  - The docstrings are the contract: link to the keyword, never restate it.
  - The mock provider is never mentioned.
  - The link form settled in Decision 4.
- **Screenshots** are taken from the demo application.

CONTRIBUTING.md §11 and `docs/README.md` point to it, and `dev-docs/README.md` lists it.

### 9. First content, kept to what is stable

- **The landing page** says what PlatynUI is for, carries the single preview notice, and links to Getting Started.
- **"What is PlatynUI?"** covers the desktop as a tree of elements, querying it, and acting like a user. It is written for Robot Framework users and mentions no internals.
- **"Installation"** covers the packages and the per-platform prerequisites, in tabs for Windows and Linux. It describes the package names and commands as they are when the page is written. The root README remains the PyPI page and keeps its own short version.
- **Later:** the tutorial and the other sections come in their own changes once `add-demo-app` exists. The first example file is the demo's launch-and-close suite, so the examples mechanism is exercised from the start.

## Risks / Trade-offs

- **[A Node toolchain in a Rust/Python repository]** → It is confined to `docs/`, has its own lockfile and recipes, and is not needed by `just check`, `just test` or any other gate.
- **[The link validator's handling of a base path]** → The first task proves the link form under both bases before any content is written, and the writing rules fix it.
- **[The examples depend on the demo application]** → The mechanism and the first example land with this change. The lane step that runs the examples is added when `add-demo-app` delivers the command, and the spec scenario for running examples is verified then.
- **[The vendored grammar ages]** → Its source commit is recorded, and updating it is one copy. A missing token class only degrades the colouring.
- **[Pages must be enabled by hand, and again after the move]** → One repository setting, noted in CONTRIBUTING.md next to the docs recipes.
- **[The keyword reference is missing until the generator exists]** → The Reference section is hidden while empty (Decision 2). Guides name keywords and gain links when the reference arrives.
- **[Drift between docstrings and site]** → The site never restates keyword behaviour; the docstrings remain the single source.

## Migration Plan

- **Additive and documentation-only.** A new Astro project, a workflow, recipes and docs. No library, binding or provider code changes; no native rebuild.
- **Rollout:**
  1. Probe the link form.
  2. Project skeleton, highlighting and the link check.
  3. Recipes and the CI build.
  4. Writing rules and the first pages.
  5. Enable Pages and deploy from `main`.
  6. Once `add-demo-app` is in: the examples lane step.
- **Rollback:** delete the Astro files in `docs/`, `docs.yml`, the docs recipes and the pointers. `docs/README.md` and `docs/talks/` return to their previous state.

## Open Questions

- The Node.js LTS line to pin in `docs/.nvmrc` is taken at implementation time, as the current LTS. It does not affect the specs.
