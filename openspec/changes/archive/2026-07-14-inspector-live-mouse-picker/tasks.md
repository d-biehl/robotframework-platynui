## 3. Real-provider hit-test: Windows UIA (self-contained)

- [x] 3.1 Implement UIA hit-test via the built-in `IUIAutomation::ElementFromPoint`, returning a node whose parent chain and runtime identity match top-down traversal. No `WindowManager` involvement — the API resolves window and in-window z-order natively.
- [x] 3.2 Verified on the real Windows UIA lane: a point over a control resolves to it ([tests/acceptance/egui/hit_test.robot](../../../tests/acceptance/egui/hit_test.robot) "Element Under The Cursor Is Resolved" passes) and the live picker resolves **and selects** the element under the cursor ([tests/acceptance/egui/inspector_picker.robot](../../../tests/acceptance/egui/inspector_picker.robot); trace shows `picker resolved element … Button` then `reveal/pick: selected row`, and the test asserts the picked control appears in the Inspector's own a11y tree). **Real bug fixed — picked node had no parent chain:** `element_at_point` resolves a node out of tree order, so it had no `parent()` chain for reveal-and-select to walk, and the picker resolved but never selected. Windows/UIA now wires the ancestor chain (`UiaNode::attach_ancestor_chain`): raw-view `GetParentElement` up to the desktop root, each level scoped `App { pid }`, capped with the synthetic `ApplicationNode`, held alive via `hold_parent` — so the scoped runtime ids match the `app:Application/<pid>/…` subtree and the existing reveal path selects it. Own UI is filtered via `CurrentProcessId == self` → nothing (the Inspector is kept off the target; the picker inspects *other* windows). **Second bug fixed — immersive shell windows were not enumerated:** the reveal needs the target's top-level window in the desktop tree, but `EnumWindows` (used to gate against the OLEACC stall) omits Win11's immersive shell surfaces — the **Start menu** / search (`Windows.UI.Core.CoreWindow`) and **taskbar / jump-list / settings flyouts** (`Xaml_WindowedPopupClass`). So the picker resolved them via `ElementFromPoint` but could never select them (absent from the tree), while Accessibility Insights shows them (it walks the UIA tree). Fixed by also enumerating those curated classes via `FindWindowExW` (`provider.rs::immersive_shell_windows`), gated on being on-screen only (they are legitimately `WS_EX_NOACTIVATE`). Verified end-to-end: the picker now selects a Start-menu item (`app/StartMenuExperienceHost`) and the taskbar menu subtree is reachable top-down. **Known Windows limitation:** a point over an *open egui menu overlay* still resolves nothing on UIA (AccessKit's `ElementFromPoint` returns the widget beneath the overlay — the reason the AT-SPI path uses a geometric search); the standalone menu-item hit-test case fails on Windows where it passes on X11. Overlapping-non-own-window and bare-desktop→nothing cases not separately scripted.

## 5. Real-provider hit-test: Linux AT-SPI

- [x] 5.1 Select the frontmost top-level window at the point via the new `window_at_point` capability (task 4), then correlate that `WindowId` to its AT-SPI top-level Accessible by PID + geometry (reusing `resolve_window`'s matching in reverse); fall back to "topmost window whose extents contain the point" if correlation fails.
- [x] 5.2 Resolve the element within the application by a **geometric bounds subtree search** (not the native `get_accessible_at_point`): walk the accessible tree reading each node's toolkit-aware `Control:Bounds` and pick the smallest-area node whose bounds contain the point. The native hit-test was abandoned because it proved unreliable across toolkits — Qt reports bad screen extents, and AccessKit returns the widget *beneath* an overlay. Scope: when a managed frame maps to the hit window, confine the search to that frame (multi-window correctness); otherwise (override-redirect popup with no managed frame) search the whole application subtree, unpruned by parent bounds, so a menu drawn outside its owning frame is still reached. A node budget guards against pathological trees.
- [x] 5.3 In-window layer disambiguation superseded by the smallest-area rule: a popup/menu item's bounds are strictly smaller than the client area beneath it, so the most-specific (smallest) containing box already wins without querying `Component.Layer`/`MDIZOrder`. (The `component_layer_rank` helper added for this was removed as unused.)
- [x] 5.4 Verified on the X11 acceptance lane (real AT-SPI): frontmost-window selection incl. a multi-top-level child dialog resolving the dialog (not the main window); element inside the window resolves; **menu-bar menu items are picked on both egui/AccessKit and Qt** (the geometric search reaches them where the native hit-test could not). See [tests/acceptance/egui/hit_test.robot](../../../tests/acceptance/egui/hit_test.robot) and [tests/acceptance/qt/hit_test.robot](../../../tests/acceptance/qt/hit_test.robot).
- [x] 5.5 Exclude hidden nodes from the result: a node whose bounds contain the point but which reports `Control:IsVisible` (or `Control:IsInView`) explicitly false SHALL NOT be picked (the accessibility tree keeps laid-out but hidden nodes with stale bounds — e.g. a closed menu's items report `IsVisible=false` with bounds `{0,0,145,26}`). Gate the candidate selection in the AT-SPI search and mirror it in the mock's `hit_test_node`; both fall through to the visible node. Covered by mock unit tests (`hit_test_skips_hidden_node`, `hit_test_hidden_topmost_falls_through_to_visible_beneath`).

## Notes

- Added a `Get Element At Point` BareMetal keyword + `PyRuntime.element_at_point` binding (beyond the proposal's "no RF keyword" note) as the acceptance-lane hook; verified via `tests/acceptance/egui/hit_test.robot` and `tests/acceptance/qt/hit_test.robot` (X11 lane, 6/6 pass: button, follows-cursor, and open menu-bar menu item on egui; main window, child dialog, and open menu-bar menu item on Qt).
- The AT-SPI in-window resolution pivoted from the designed native `get_accessible_at_point` descent to a geometric smallest-area bounds subtree search (see task 5.2) after the native path proved unreliable on Qt (bad screen extents) and egui/AccessKit (returns the widget beneath an overlay). The switch also made menu-bar menu items pickable on both toolkits.
- **Known limitation — transient context menus:** not pickable by this top-down resolver, but NOT because the toolkit hides them. On Qt the popup *is* exposed on AT-SPI, event-driven: while an AT client is registered for events, a `PopupMenu` appears as a child of the `Application`, reachable via the hovered item's `parent()` chain and via `getChildren` down from the popup — but absent from the `Application`'s own top-down `getChildren`, so the geometric bounds walk misses it (a screen reader following children-changed / state-changed:showing events finds it). Verified in the X11 lane with an AT-SPI event watcher (`crates/provider-atspi/examples/atspi_focus_watch.rs`). Picking context menus needs event-driven tree updates in the provider, tracked as the separate `atspi-event-driven-tree` change; the Qt test app keeps a realistic right-click context menu as the fixture.
- **Windows acceptance-lane plumbing (fixed while verifying 3.2):** the lane could not run on Windows. (1) `just test-acceptance-windows` never built the Inspector binary nor set `PLATYNUI_INSPECTOR_BIN`, so `inspector_picker.robot` had nothing to launch; the recipe now `cargo build -p platynui-inspector` and hands over the absolute `.exe` (same for the Linux `scripts/platynui-robot-session.sh`). (2) The default `${TEST_APP_BIN}` / `${INSPECTOR_BIN}` Robot vars were relative, forward-slash, `.exe`-less paths — `Start Process`/`CreateProcess` will not launch those on Windows even when the file exists; they now resolve to an absolute, OS-native path (`.exe` on Windows) via an inline `os.path.abspath(...)` expression, honoring the env-var override. With these, the egui hit-test + inspector-picker suites run and pass on the real Windows desktop.
- **Third bug fixed — the picker made the tree grow/churn.** Two causes, both surfaced once picking actually worked and amplified by the immersive-window change:
  - *Root re-enumerated every tick.* `reveal_task(refresh=true)` blindly `clear_children_cache()` on **every** level of the path, including the desktop root — on **every** picker tick. Moving the cursor over a (modal) menu re-enumerated the whole desktop repeatedly; while the modal loop blocks UIA the reload returns partial/empty, so the top-level window/app list flickered "mal mehr mal weniger, bis garkeine" and menu entries didn't appear. Fixed in [async_tasks.rs](../../../apps/inspector/src/viewmodel/async_tasks.rs): try the cached children first and refresh a level **only when the wanted ancestor/target is missing** (a just-opened window/menu). Verified via the taskbar Xaml-popup menu (same mechanism as the desktop context menu): the root is now refreshed **0×**, only the menu window itself reloads, and the hovered item selects (`reveal/pick: selected row`).
  - *Expanded paths accumulated.* The reveal expands every ancestor and never prunes; the picker reveals on every element the cursor passes, so expanded paths piled up. Fixed by snapshotting the expansion when the picker arms (`InspectorViewModel::picker_reveal_base`) and resetting to it before each pick (`TreeViewModel::{expanded_ids, set_expanded_ids}`), so picking shows only the current element's path; the last pick persists after disarm.
- **Fourth bug fixed — dynamic-menu items never appeared (unstable RuntimeIds).** Picking an item in a Windows shell context/Start-adjacent menu **or a VS Code / Chromium menu** resolved the element but nothing showed in the tree. Root cause: those XAML/Chromium menus hand out **unstable UIA RuntimeIds** — the id reached via the hit-test's `GetParentElement` walk differs from the id the same item gets via `GetChildren` (confirmed by trace: chain wanted `…4007c.4.7e`, the menu window's children were `…4.1/.21/.1d/…`). The reveal matches by RuntimeId, so it always diverged and gave up. Fixed by **grafting the picker's already-resolved live chain** into the tree at the divergence point (`UiNodeData::graft_chain` + `async_tasks::resolved_chain_below`) instead of cancelling — the same reason Accessibility Insights works (it holds the live element rather than re-matching ids). Verified on the taskbar Xaml-popup menu: the item now reveals and selects (`Window → Menu → Menuitem → Text "Task-Manager"`). The graft only triggers on divergence, so normal reveals (egui/`inspector_picker.robot`) are unaffected. Unit-tested with a minimal mock `UiNode` (`tree_data::test_mock`): `resolved_chain_below` returns the correct top-down slice and `None` off-chain; `graft_chain` nests the subtree, leaves the leaf lazy, and dedupes the top.
  - `inspector_picker.robot` still passes.
- **Fifth bug fixed — a phantom "invisible" window in the tree.** The desktop tree showed a top-level `Window` with `0×0` bounds and `Control:IsVisible=false` (Win32 `IsWindowVisible` true but UIA-invisible, zero-area). The enumeration now drops zero-area windows (`provider.rs::window_has_area`, applied to both the `EnumWindows` population and the immersive shell classes). Verified: the phantom window is gone, real windows remain, egui tests green.
- **Known limitation — Chromium menu-bar dropdowns (e.g. VS Code File/Edit menus).** The dropdown opens and its items are in the tree, but Windows UIA `ElementFromPoint` returns the widget **beneath** the menu overlay (confirmed: over `MenuItem "New Text File"` it resolves the `SOURCE CONTROL` panel / an `Extensions` toolbar). So the picker resolves the wrong element *before* reveal/graft — this is the same "returns the widget beneath an overlay" issue the design records for egui/AccessKit, here in Chromium. VS Code **context** menus and the Windows **shell** menus resolve correctly; only Chromium **menu-bar** overlays are affected. Working as designed for the Windows native-`ElementFromPoint` path; the AT-SPI-style geometric hit-test that would fix it was explicitly declined for this change (kept the native path). Accessibility Insights, which also uses `ElementFromPoint`, has the same limitation on these overlays.

Still open: the full interactive picker acceptance suite beyond `inspector_picker.robot`; macOS/generic-Wayland greyed-out gating (part of 10.2) unverified on real hardware.
