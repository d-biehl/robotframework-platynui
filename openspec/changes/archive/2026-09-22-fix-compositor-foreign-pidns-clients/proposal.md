# Proposal

## Why

The PlatynUI Wayland compositor aborts — taking every application in the session with it — as soon as it has to report anything about a Wayland client whose process it cannot resolve. `window_pid` (`apps/wayland-compositor/src/control.rs:1277`) asks `wayland_server::Client::get_credentials`, which reads `SO_PEERCRED` through `rustix`. A peer that lives in a PID namespace the compositor cannot see is reported by the kernel with PID `0`, and the `rustix` 1.1.4 that `wayland-backend` 0.3.15 links reads it into a `UCred` whose `pid` is a non-zero `Pid` (`rustix-1.1.4/src/net/types.rs:2096`) through `assume_init` (`rustix-1.1.4/src/backend/linux_raw/net/sockopt.rs:45-61`). The value cannot be represented, so the read is undefined behaviour; in the measured build it surfaced as an `Err`, and `wayland-backend-0.3.15/src/rs/server_impl/client.rs:314` panics on its `.expect("getsockopt failed!?")`. The first panic poisons the backend mutex, the next `poll_fd()` unwraps that error, and the panic inside the destructor turns into a process abort.

This was measured in a podman pod with the compositor and a client in sibling PID namespaces: the foreign client maps a window and the session stays healthy for 15 s with nothing querying; a **single** `list_windows` kills the compositor, and with it the locally running application and every other client. The same abort was reproduced through the real CLI, where the provider calls `list_windows` to resolve a window.

This is the first step of the Kubernetes sidecar deployment (the runtime in a sibling container, the display server and the application in the app container), and it must land **before** `wayland-sidecar-capabilities`: today the provider fails compositor detection across the namespace boundary and therefore never issues a window query, so the crash stays latent. Teaching the provider to detect the compositor first would turn a silent degradation into a reproducible session crash on every window query.

The same question — which process is on the other end of this connection — is what the compositor needs to do the other thing `element-at-point` has always required of a window system that can see the stack: "an own-process window at the point SHALL be skipped so the window **behind** it is resolved". `window_at_point` (`src/control.rs:565-579`) hands back whatever `Space::element_under` finds in front, including a window of the very process that asked. Until this series it was an unowned divergence from `element-at-point`; `wayland-sidecar-capabilities` now lists it among the divergences that have found an owner, and that owner is this change. Measured in the podman pod: the compositor returns the caller's own window and the AT-SPI provider's own-process guard (`crates/provider-atspi/src/lib.rs:317`) then discards it, so the picker ends up with nothing — where X11's window manager already returns the window behind. That provider-side guard is being dropped (`atspi-process-identity`), settled with the maintainer: the display server, not the provider, is what can tell whose window a window is. Dropping it while the compositor still returns the caller's own window would turn today's "nothing" into the Inspector picking itself — a regression. The exclusion therefore belongs here, in the one place that already holds both identities.

## What Changes

- **Client identity is captured when the connection is accepted.** The compositor reads the peer credentials itself at the one place where it still owns the accepted socket — the Wayland listening socket before `insert_client` (`src/backend/mod.rs:204-206`) and the `wp-security-context-v1` listener (`src/handlers/security_context.rs:28-31`) — and stores the result with the per-client data (`src/client.rs`). It is read back through `client.get_data::<ClientState>()`, the pattern already used at `src/handlers/compositor.rs:27`.
- **No control command asks the Wayland backend for credentials any more.** `window_pid` (`src/control.rs:1277`) uses the stored identity, so the five commands that build window information — `list_windows`, `get_window`, `window_at_point`, `list_popups` and the minimized-window listings (`src/control.rs:1084/1203/1236`) — cannot abort. `SecurityPolicy::is_client_allowed` (`src/security.rs:101`), the second use of the same accessor, uses it too; under a restrictive policy an unidentifiable client stays denied, as today, but without the abort.
- **An unresolvable PID is `null`, never `0`.** PID `0` and any failed credential read mean "unknown". The IPC structs already type the field as `Option<u32>` (`src/control.rs:140/175/193`) and the only consumer already models it as an option (`crates/platform-linux-wayland/src/window_manager/platynui_ipc.rs:18/29`), so this constrains the value domain rather than the wire schema.
- **The window at a point is never the caller's own window.** `window_at_point` (`src/control.rs:565-579`) walks the stack from the front instead of taking `Space::element_under`'s first hit, skips a window whose Wayland client is the same process as the peer of the control connection the request arrived on, and returns the window **behind** it (or nothing, when there is none). Both sides of the comparison are the compositor's own view: the identity captured at accept time above, and the peer credentials of the accepted control connection (`ControlClient`, `src/control.rs:219-228`, accepted at `:260-265`). The exclusion happens **only on a positive match** of two identities the compositor could establish — when either side is unknown, or when the window's process is merely what an XWayland client declared about itself, nothing is excluded, because answering with an occluded window on the strength of an unresolved identity is worse than answering with the caller's own. Only the point lookup excludes; the listings keep reporting the caller's windows.
- **XWayland stays a separate source.** An XWayland-backed window keeps reporting the X11 client's declared `_NET_WM_PID` (`smithay-0.7.0/src/xwayland/xwm/surface.rs:372`). XWayland's own Wayland connection is never reported as a window's PID, and the two sources are not mixed.
- **Diagnosability.** The identity decision is logged once per client at accept time, so a session in which every client is unidentifiable is visible in the log instead of only in the consequences.
- **The panicking accessor is banned.** `wayland_server::Client::get_credentials` goes into `clippy.toml`'s `disallowed-methods`, next to the existing `disallowed-types` entries, so the abort cannot be reintroduced. The matching ban for `rustix::net::sockopt::socket_peercred` is deliberately **not** added here: `crates/platform-linux-wayland/src/capabilities.rs:67` still calls it and `just clippy` runs `-D warnings` over the whole workspace, so that entry belongs to `wayland-sidecar-capabilities`, which rewrites that function.
- **Not BREAKING.** For a client the compositor can resolve, every response keeps the values it has today (guarded by the existing `ipc_tests.rs:635` assertion, which expects the test process's own PID). Two behaviours change: an abort disappears, and `window_at_point` stops answering with the caller's own window — which is what the `element-at-point` capability already required and no consumer can have been relying on, the only consumer being a picker that wants the window behind.

Explicitly **out of scope**, owned elsewhere:

- Compositor **detection** from a foreign namespace, the `CompositorType::Unknown` degradation and the resulting wrong window bounds — `wayland-sidecar-capabilities`.
- The AT-SPI own-process filter, the `/proc`-derived `app:*` attributes, and dropping the provider's own hit-test guard (`crates/provider-atspi/src/lib.rs:317`) — `atspi-process-identity`.
- The X11 `window_at_point` self-skip and its XRes gate — `x11-window-owner-identity`.
- Running namespace tests in CI — `evaluate-pidns-tests-in-ci`.

## Capabilities

### New Capabilities

- `compositor-client-identity`: how the PlatynUI Wayland compositor determines, stores and reports which process a Wayland client belongs to — when identity is established, what happens to commands when it cannot be established, how an unknown process is represented on the IPC wire, how XWayland windows differ, and what the compositor answers at a point whose frontmost window belongs to the process that asked.

### Modified Capabilities

None. `compositor-popup-geometry` requires the popup listing to carry the parent toplevel's window id and process id, and that stays true: the field is still there and still carries the resolved PID for every client the compositor can resolve. The new capability defines the *value* of that field when the process cannot be resolved, which the popup spec does not state. `compositor-modifier-state` does not touch client identity at all.

`element-at-point` is not modified here either, although the own-window exclusion is what closes its long-standing gap on Wayland: its requirement *Hit-test excludes the host process's own UI* already says an own-process window at the point is skipped so the window behind is resolved, and this change makes the compositor satisfy that wherever identity exists — the same namespace, and a caller in a child namespace. The wording of that requirement is being rewritten by `x11-window-owner-identity` (ownership is what the window system attributes to our own connection, never a self-reported number); two changes must not rewrite the same requirement, and the new requirement here is about the compositor's control socket, not about the provider-level hit-test.

## Impact

- **Rust, `apps/wayland-compositor` only:**
  - `src/client.rs` — `ClientState` carries the captured identity; the peer-credential read lives here.
  - `src/backend/mod.rs`, `src/handlers/security_context.rs` — capture at both accept sites.
  - `src/control.rs` — `window_pid` reads the stored identity; `ControlClient` (`:219-228`) carries the identity of its own peer, captured where the control connection is accepted (`register_control_client`, `:285`) and passed into `process_command` (`:382`), which today knows only the request text; `window_at_point` (`:565-579`) uses it to skip the caller's own windows.
  - `src/security.rs` — the policy check reads it too.
  - `Cargo.toml` — a direct `nix` dependency with the `socket` feature, for a `SO_PEERCRED` read that can represent `0` without `unsafe`: `nix::sys::socket::getsockopt` with `sockopt::PeerCredentials` wraps a plain `libc::ucred`. Neither `rustix` version can represent `0`, `std`'s `UnixStream::peer_cred` is unstable (`peer_credentials_unix_socket`, rust-lang/rust#42839), and reading through `libc` directly would need an `unsafe` block, which the maintainer prefers to avoid where a safe wrapper exists. `nix` is new to the lock; it sits on the `libc` the workspace already builds.
- **Workspace lint configuration:** `clippy.toml` gains one `disallowed-methods` entry; the root `Cargo.toml` `[workspace.lints.clippy]` gains `disallowed_methods = "deny"` alongside the existing `disallowed_types = "deny"`.
- **Tests:** unit tests for the credential-to-identity mapping, for the serialized `null` and for the exclusion decision, all in `just test`; an `ipc_tests.rs` test for the own-window exclusion, which needs no namespace at all — the test process maps its own window and asks over it, so the positive match is the *default* lane's topology; one namespace integration test that runs the compositor inside a user+PID namespace, `#[ignore]`d and reachable through a `just` recipe, because unprivileged user namespaces are not available everywhere (AppArmor blocks them on stock Ubuntu 24.04 — measured). Where a prerequisite is missing — user namespaces blocked, `unshare` absent, a compositor that cannot start — that test **fails** with a message naming it and never skips, following the Java agent's live checks (`crates/java-agent/tests/live_fixture.rs`, `justfile:403-404`: "a missing artifact fails the run rather than silently skipping the coverage"). The existing `ipc_tests.rs` tests keep their graceful skip unchanged.
- **Docs:** `apps/wayland-compositor/docs/ipc-protocol.md` — the `pid` field is nullable and what its two sources are; `window_at_point`, which the document does not describe at all today, gains a section stating the exclusion rule.
- **Platforms and providers:** Linux/Wayland only; the compositor builds nowhere else. Windows UIA, macOS AX, X11 and the mock are untouched.
- **No native rebuild:** nothing in `packages/native`, `src/PlatynUI` or the Robot Framework surface changes; the acceptance lanes keep running against the same IPC contract.
- **Consumer:** `crates/platform-linux-wayland` needs no change here. Its window matching already handles a missing PID (`platynui_ipc.rs:332-337/381`); how well it matches *across* namespaces is `wayland-sidecar-capabilities`' problem. It also needs no change to benefit from the exclusion: it opens a fresh control connection per command (`src/control_ipc.rs:10-21`), so every `window_at_point` (`platynui_ipc.rs:212-241`) already arrives on a connection whose peer *is* the runtime asking.
