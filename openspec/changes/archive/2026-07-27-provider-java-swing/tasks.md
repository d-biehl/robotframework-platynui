## 2. Provider: client and mapping

## 3. Routing

- [x] 3.1 Backend routing (design 4): the router prefers the agent backend when the agent-present signal holds, else JAB; a mid-session agent appearance switches the serving backend on the next enumeration pass; `window_claims` untouched
    - **Reshaped as follows (answering the constraint this task carried).** Selection became the backend's *input*, not a filter on the router's output. The two open questions resolved to: the agent backend serves **whole windows** (`Window.getWindows()` is the JVM's own list), and the app-grouping interaction is settled by the exclusion being *live* rather than a snapshot — a `JabAppNode` enumerates its windows lazily, after the pass that produced it returned, so a post-filter provably could not reach them. Concretely: `BackendOwnership` (router) maps window → backend **rank**, updated right after each backend enumerates so the next one already sees it *in the same pass*; each backend holds a `ForeignWindows` view of it and drops what a stronger rank owns; the JAB crate takes it as a `WindowExclusions` hook consulted in discovery, in the app node's lazy children, and in hit-testing. Ownership is **preference-aware, not first-come** — "already owned" cannot be the exclusion rule, or a mid-session agent could never take a window over from the incumbent bridge. `Enumeration` kept its flat node list; what it gained is `java_processes`, for a different reason (see 3.3).
- [x] 3.2 Routing is automatic — no attach/connect keyword anywhere in the user-facing surface
- [x] 3.3 `providers.java.agent.auto_attach` (**default on**, design 4): an enumerated Java window whose JVM carries no agent gets one injected via the `java-agent-core` transport; `false` limits the agent to `-javaagent`-launched targets

## 4. Acceptance & verification

- [x] 4.2 A Swing application started by its own script, with no PlatynUI arguments, is served through the agent backend without being restarted
- [x] 4.3 Routing: a JVM with the agent is served via the agent backend (single representation — one Java claim, one tree); a no-agent JVM is still served by the JAB backend
- [x] 4.4 Node lifetime: a scoped root pinned to an agent-served element is re-resolved after its window closes and reopens (the agent-backend counterpart of the JAB proof in the Swing window lane), and a killed JVM does not leave a root reported valid

## Notes

- **Highlighting is not the agent's** (1.4, corrected during implementation). An in-JVM overlay window was built and then removed: `HighlightProvider` is a *platform* capability and drawing belongs there. What the Access Bridge lacks for a table cell is **bounds**, not a way to draw — so supplying bounds fixes the picker for every consumer at once, and the agent never paints into the application it observes (nor leaves it visibly changed if a run dies mid-pick).
- **`--add-opens` turned out not to be needed at all** (1.5). The measurement first showed the expected matrix — on JDK 21 the handle needs `java.desktop/java.awt` **and** `java.desktop/sun.awt.windows` opened, one for the peer field and one for the peer method — and then that the whole question is avoidable: an instrumentation agent may open packages to itself via `Instrumentation.redefineModule`, which is what JEP 261 gave agents that power for. The command-line remedy was never available to this design anyway (attaching to a running JVM means PlatynUI does not own the launch line). This moves 2.4's fallback back to being a genuine fallback rather than the everyday path on modern JDKs. Full matrix in design.md.
- **A window is named by its title, not by `Component.getName()`** (2.2). Caught by the live test, and it would have been silently destructive: AWT *manufactures* a component name for every unnamed `Frame` (`"frame0"`), so preferring the component name renamed every Swing window and broke every `//Window[@Name=…]` locator. Fixed twice over — the agent reports `getName()` only when `Component.nameExplicitlySet` says the application set it (exact, not a guess about name shapes), and the mapping layer names a top-level by its title regardless.
- **A table cell is `item:TableCell`, not `control:Label`** (2.2, deliberate divergence from the JAB backend). Swing reports a cell with the shared renderer's role; carrying that through would import the bridge's defect into a backend that does not have it. Existing suites address cells positionally, so nothing that worked stopped working.
- **`auto_attach`'s trigger is "this JVM has no agent", not "no backend serves this window"** (3.3). It was first wired to the unserved-window list, which the live test exposed as wrong: a bridge-served window still has a better representation available, so gating on unserved windows would have limited automatic attachment to JVMs that were already broken. `Enumeration` therefore gained `java_processes` — the processes behind every Java window a backend *saw*, served or not. The agent backend cannot produce that list itself: it discovers agents, not windows.
- **Consequence of `auto_attach` defaulting to on**: a Swing JVM does not *stay* agent-less, so a test that wants the Access Bridge has to say so rather than rely on an absence the provider is actively removing. The Swing acceptance suites and the JAB-focused live fixtures now set `providers.java.agent.enabled = false` explicitly — they assert bridge behaviour (renderer-aliased cell names, JAB role quirks) and remain valuable as bridge coverage. Agent behaviour is covered by the four new live fixtures.
- **The role vocabulary is shared, the mapping is not** (2.2). The agent emits `Locale.ENGLISH` role/state display strings, which *are* JAB's `role_en_US`/`states_en_US`, so a locator keeps matching when the serving backend changes. The mapping table is duplicated in `provider-java/src/agent/element.rs` rather than imported from the JAB crate, because the router has to become portable (`java-provider-linux`) while that crate stays Windows-only. Consolidating them is a follow-up for when the shared layer has an obvious home.
- **The attach now takes effect in the pass that triggered it** (3.3, added after the first interactive check). Attaching at the end of a pass meant the *next* pass was the first to serve through the agent — in the Inspector: `JAB`, refresh, `JavaAgent`. The router now waits (bounded) for the injected agent's handshake file and re-sweeps the backends, discarding the first sweep rather than editing it: which node stands for which window is precisely what a flat node list cannot answer, and the second sweep needs no special case because the agent records those windows at its own rank first. Attachment is retried up to `MAX_ATTACH_ATTEMPTS` times per JVM, because one transient failure must not cost an application the agent for a whole session. Recorded in design.md.
- **The node contract was never verified for agent nodes — and it was violated** (2.2, found by asking after the pattern surface). `control:SupportedPatterns` is `required` in the testkit's `COMMON_ATTRIBUTES`, and the agent node did not emit it. It went unnoticed because the contract testkit only ever ran in `live_fixture_contract_and_interaction`, which is a JAB scenario; nothing ran agent nodes through `validate_control_or_item` / `verify_common_attributes`. That check now runs over the agent's whole tree, and it is the test that will catch the next one. Fixed alongside: `toggleable::ToggleState`, `expandable::IsExpanded`/`CanExpand` and `activation_target::ActivationPoint`, all of which the JAB backend published and the agent did not — so the same element answered different questions depending on which backend served it, which is exactly what the shared vocabulary exists to prevent.
- **Why the *set* of patterns stays small** (2.2). PlatynUI's production pattern vocabulary is `Focusable` plus the window family; `Toggleable`, `TextContent`, `Clearable` and `ActivationTarget` exist as identifiers with attributes but no action instances in any real provider. Going beyond that is not an implementation gap but a policy decision: the agent *could* implement Toggleable in-process (`AbstractButton.doClick()`), and that is precisely what `text-input-policy` forbids for text — a programmatic state change takes a different path through the application than a user does. The agent therefore publishes toggle/expansion/selection as **attributes** and leaves the acting to real input, matching the JAB backend.
- **TextContent is synthesised from `control:Text`, and an empty field was dropping it** (2.2). PlatynUI's client layer derives five capabilities from a sentinel attribute rather than from `SupportedPatterns` (`_ATTRIBUTE_ONLY_PATTERNS`: `Element`←`Bounds`, `ActivationTarget`←`ActivationPoint`, `Readable`←`IsReadOnly`, `TextContent`←`Text`, `WindowState`←`IsActive`) — which is why no provider advertises them and why that is not a gap. The agent did drop one, though: it omitted `text` when the value was *empty*, so an empty `JTextField` looked like a label and `supports_pattern(TextContent)` answered false on something the user can type into. The field is now present whenever the element has text capability, with `""` meaning "empty" and absence meaning "no text at all". Verified through the Python adapter against the live fixture: all five resolve on agent-served nodes.
- **Review pass, three more defects — all in already-green code** (2.2). (a) A table cell published its *model value* as `control:Id`, so `//*[@Id="r2c1"]` matched something whose "id" changes when the data does; `stable_id()` is now restricted to real components, where `name` really is a developer-set `Component.getName()`. (b) `control:SelectedItems` was assembled from a parallel id scheme (`agent/<pid>/child/<index>`) and named **no existing node** — it now carries the same ids the child nodes carry, sourced from `SwingTree.childAt`, the very function the tree hands children out of, and is *omitted* where the accessible order and the tree order cannot be shown to agree rather than guessed at (the raw indices survive as `native:Selection.Indices`); the scan is bounded at 512 and truncation suppresses the list rather than shortening it silently. (c) An element that was never laid out — a menu item whose popup has not been opened — reported a `0x0` rectangle at its owner's corner, which aimed the pointer at the menu bar and let the Element capability resolve on something with no place on screen; an empty rectangle is now no rectangle. Each is pinned by a live assertion. Also deleted: a `provider_error` helper that nothing used, kept compiling by a `const _` that referenced it.
- **Dev-loop hazard worth knowing**: `just build-java-agent` rebuilds the JAR, but the *installed* package keeps serving the staged copy until `just build-provider-java` restages it — and the provider↔agent version handshake cannot catch this, because both sides still report the same dev version. It cost two confusing verification rounds during this change. `just install-provider-java` does both.
- **The agent's containment had no live test, and writing it found a defect** (4.6). `live_frozen_jvm_stays_contained` was always JAB's; the agent's degraded-session path was correct only by construction. The agent counterpart (`live_frozen_agent_stays_contained`, same `set_process_frozen` freeze) failed immediately at the recovery step: **the session never came back**. A call abandoned at its deadline leaves the TCP stream desynchronised — the agent writes that answer later and the next call reads it as its own, the client reports the crossed ids, and no amount of retrying un-crosses them. So one wedged moment cost that JVM the rest of the run. The session now drops a connection that timed out and rebuilds it from the handshake file, and the test pins both halves: bounded failure while frozen, usable again after thawing.
- **The spec delta described a mechanism that was not built** (3.1). It said backend selection detects the agent "via `java-app-classification`"; the implementation uses the agent's own handshake rendezvous (`handshake::agent_present`), deliberately — a platform Java classifier exists only on Windows, and `java-provider-linux` depends on the criterion being available without one. The requirement now says what exists, and the attach scenario says "in that same enumeration" rather than "on the next pass".
- **The toolkit belongs in `native:JvmToolkit`, not in `@Technology`** (2.2). `@Technology` names the channel that surfaced a node, and that is load-bearing: it is what distinguishes an agent-served window from a bridge-served one, which the dedup and routing suites assert on, and `//*[@Technology="JAB"]` is an exact match that folding the toolkit in would break. The toolkit already had a canonical home whose own documentation said the authoritative answer "requires an in-JVM agent (forward design)" — and the agent backend was publishing none of those facts. It now publishes `IsJvm`, `JvmToolkit` (loaded-class detection mapped onto the shared `Swing/AWT` / `JavaFX` / `SWT` labels, so the string does not depend on who served the window) and `JvmAgentPresent`, plus the raw set as `native:JvmToolkits` for the deferred mixed-toolkit case. `JavaFX` and `SWT` need no new mechanism when their adapters land — only their toolkit name in the detector. `JvmAccessibilityReachable` stays absent: it is about native accessibility, which the agent is not, and absent beats guessed.
- **Column headers had no bounds and were labels** (1.1, fixed here as a defect). Swing's `AccessibleJTableHeaderEntry` answers the renderer's role (`label`) and a **zero-height** rectangle, because the renderer it delegates to was never laid out — so a header arrived as a label with no place on screen, although sorting, resizing and reordering all happen there. Same defect class and same remedy as the cells this change exists for: read the header component instead of its accessible wrapper (`JTableHeader.getHeaderRect`, and the column model for the value). Now `item:ColumnHeader` with a real rectangle, plus `native:ColumnHeader.Column`/`.ModelIndex`/`.IsResizable` — the model index because it is the one that survives the user dragging columns around. **Deliberately not** included: row grouping and tree hierarchy — see the note below.
- **Verified live** (21/21 real-provider fixtures, 97/97 Windows acceptance): the JTable cell with its own name/bounds/selection and a RuntimeId stable across enumerations (4.1); a JVM launched with no PlatynUI arguments attached in-place and served through the agent **on the first pass that shows it**, same pid (4.2); one window, one representation, with the bridge taking over when the agent is off (4.3); a killed JVM leaving no node reporting valid, boundedly (4.4).
- **The HiDPI verification moved out** (1.3). It could not be done here — this host reports 96 DPI and JDK 17 was absent — and rather than archive a checked box over an unmeasured claim, it became `verify-display-scaling`. That change is deliberately wider than this one: the blocker is a *scaled display*, and the same display covers UIA and the JAB backend, whose scaling has never been measured either. The finding that motivated widening it: JAB's per-window DPI transform is documented as *identity at 100 %*, so that entire calibration mechanism has never executed on a development or CI machine.

## Out of scope, and why (recorded for the follow-up proposal)

Reviewing the table surface surfaced three wishes that do **not** belong in this change:

- **Tables as `Row` → `Cell` instead of a flat cell list.** This changes the *shape* of the tree: the acceptance suites address cells positionally (`//*[@Name="main-table"]/*[8]`), the `native:TableCell.*` assumptions shift, and RuntimeIds change. More importantly it is a **core-vocabulary decision, not a Java one** — UIA has Grid/GridItem, AT-SPI has its table interfaces, and there is no `item:Row` in `pattern_names` or the role map. If only the Java agent invents row nodes, the same logical table looks structurally different depending on which provider served it, which is the exact divergence this change spent its review budget removing.
- **Tree hierarchy and sub-items.** The accessible view of a `JTree` is a *flat list of visible rows*; a real hierarchy means walking the `TreeModel`, with its own identity scheme (a `TreePath`, not an index). Genuinely the kind of thing an in-JVM agent can do and a bridge cannot — and genuinely new tree-reading logic.
- **Fixture work.** `apps/test-app-swing` has **no** `JTree`, `JList` or `JTabbedPane` at all (verified). There is nothing to develop the above against and nothing to verify it with, so the proposal has to carry the fixture extension.

The three share one prerequisite — how PlatynUI models item-bearing and hierarchical controls *in general* — so they belong in one proposal rather than three, and that proposal starts in the core vocabulary rather than in the Java agent.
