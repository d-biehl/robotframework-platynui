# Proposal

## Why

The four fixes that make PlatynUI usable from a sibling container — `fix-compositor-foreign-pidns-clients`, `atspi-process-identity`, `wayland-sidecar-capabilities` and `x11-window-owner-identity` — all carry regressions that only appear when the runtime and the application sit in **different PID namespaces**. Every fact we have about that topology was produced by hand: podman pods, an `unshare` harness inside a VM, and a kernel-6.8 VM for the pidfs trap. Those changes therefore land their integration coverage locally: unit tests in the normal suites, plus an `unshare`-based harness behind a `just` recipe and `#[ignore]`d tests that fail, never skip, when a prerequisite is missing. They follow the precedent of the Java agent's live checks (`crates/java-agent/tests/live_fixture.rs`, `just test-java-agent-live`). Local-only coverage is a regression risk we accept knowingly, not one we should accept silently: `dev-docs/testing-strategy.md` §6 asks that no automated lane stay ungated.

Whether a GitHub-hosted runner can run that harness is genuinely unknown today, and exactly one fact decides it. Stock Ubuntu ships `kernel.apparmor_restrict_unprivileged_userns = 1`, and on a 24.04 VM this was **measured** to block the harness's own invocation (`unshare --user --map-current-user --keep-caps --pid --fork --mount-proc` → `write failed /proc/self/uid_map: Operation not permitted`, `apparmor="DENIED" … profile="unprivileged_userns"`). The usual remedy is one `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`. The runner has passwordless sudo, but **no public log shows the live sysctl values or a successful `unshare -Ur` on a hosted runner**, and the runner-images build scripts never touch those sysctls. That is a five-minute measurement and a decision, not a design problem — so it gets its own change instead of blocking the fixes.

Background, not a driver of this change: GitHub has announced that `ubuntu-latest` moves to Ubuntu 26.04, rolling out between **2026-10-19 and 2026-11-19** ([actions/runner-images#14748](https://github.com/actions/runner-images/issues/14748)). The Linux jobs in `.github/workflows/ci.yml` run on `ubuntu-latest`, so their stock bus moves from dbus-daemon 1.14.10 to 1.16.2. The normal lanes are unaffected by that: application and runtime share a PID namespace there, and the daemon differences recorded in `design.md` concern a peer the bus daemon cannot see, which a normal lane does not have. The jobs stay on `ubuntu-latest` (maintainer decision), and this series makes no runner decision.

## What Changes

- **A research spike, on a throwaway branch, before anything is adopted.** One workflow job, on `ubuntu-latest` like the existing jobs, prints `sysctl kernel.apparmor_restrict_unprivileged_userns kernel.apparmor_restrict_unprivileged_unconfined`, runs `unshare -Ur id`, applies the sysctl, and then runs the `unshare` harness that `atspi-process-identity` owns against the runner's stock bus — its recipe takes the daemon as a parameter, so this is `just test-atspi-pidns dbus-daemon`. The job logs, per topology, the daemon and its version, the decided identity mode and its inputs. It asserts only verdicts that hold on any bus: no foreign peer is claimed as our own, and our own peer is recognised where the bus identifies it. Whichever image `ubuntu-latest` resolves to during the rollout, the job therefore checks the same thing.
- **A fallback variant is measured in the same spike, not assumed**: if the sysctl is refused or does not take effect, run the harness as `sudo unshare …` and drop back to uid 1000 with `setpriv` inside the namespace, so every D-Bus peer authenticates as the same uid (EXTERNAL auth) as in the measured setup. This variant has **never been run**, here or anywhere.
- **Runtime and flakiness are measured, not estimated.** Earlier estimates put the harness at "seconds of runtime"; no wall-clock number was ever recorded. The spike records the job's wall time over at least five runs. It also records whether the forced-PID step (a helper that forks until a child lands on the target PID) is deterministic when it runs first in a fresh namespace. Forced PIDs were measured to be *not* deterministic once anything else spawns threads there: 600 forced spawns under steady and burst thread churn needed up to 7 attempts each (~5.5 % miss per attempt). The harness must therefore take its PID before anything else starts and keep a bounded retry.
- **A decision point with a written outcome, either way.** Green and fast (single-digit minutes, no flakes over five runs) → adopt one job, on the runners the existing jobs use. Refused, contorted (a chain of sudo/setpriv workarounds), or flaky → the tests stay local and the decision is recorded with its reason. Both outcomes end in `dev-docs/testing-strategy.md`; the "no" outcome is a legitimate result of this change, not a failure of it.
- **Conditional adoption, without a runner decision.** If adopted, the job runs on `ubuntu-latest` like the other Linux jobs in `ci.yml`. Its assertions do not depend on the daemon, so the label's move to 26.04 changes which bus it exercises, not what it asserts. A failure that shows up only after the move is a finding for `atspi-process-identity`, not a reason to pin.
- **Daemon-specific cells stay out of CI and are covered where they already are.** Which identity mode a particular bus produces is covered by unit tests over the recorded credential shapes (owned by `atspi-process-identity`) and by the local podman image matrix, not by choosing, pinning or provisioning runners. That covers dbus-daemon 1.12/1.14 (`ProcessID = 0`), dbus-daemon 1.16.2 (`ProcessFD` plus `UnixProcessIdUnknown`) and dbus-broker 29/33. It also covers dbus-broker 35/37, which answers `GetConnectionUnixProcessID` with a **successful 0** while omitting `ProcessID` — the exact cell where PR #5's approach computes `Some(0)` and drops a foreign application (measured: 2 applications on `main`, 1 with PR #5, with no PID collision at all).
- **What stays untestable on hosted runners is named and re-homed, not silently dropped**: a pre-6.9 kernel. Both images `ubuntu-latest` resolves to around the rollout run kernels ≥ 6.17, so the anon-inode trap where *every* pidfd has `st_ino=69` is unreachable there. It belongs in a unit test with an injected `f_type`, owned by `atspi-process-identity`.
- **Out of scope, explicitly:** the pod-lane/acceptance-lane architecture with podman, a second display server and a fixture-launch bridge. It was evaluated and rejected: ~1 GB images, an X server or software-GL compositor, and on 26.04 a 15 s teardown stall per rootless container (AppArmor blocks podman's SIGTERM to `pasta`, LP #2154379). Also out of scope: the harness and the unit tests themselves (owned by changes 2–4), the Wayland/X11 fixes' own coverage, and any choice of runner for existing or new jobs.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. **`skip_specs: true`** is set in this change's `.openspec.yaml`.

The decision is deliberate. This change produces a CI job, a `dev-docs` decision entry and — in the "no" case — nothing but documentation. It adds no product behaviour and changes none. The one capability that could plausibly be touched, `acceptance-lane-selection`, is about how Robot Framework *acceptance suites* declare platform tags and how `robot.toml` profiles select them and establish their session. The PID-namespace coverage is Rust `#[ignore]`d tests plus a shell harness with no RF suite, no tag and no profile, so adopting it in CI neither adds a lane nor changes how lanes select. Inventing a requirement here would put a workflow file's job list under a behaviour contract it does not belong in. If the spike's outcome unexpectedly requires an RF acceptance suite to run in a PID-namespace topology, this decision must be revisited before the change is applied.

## Impact

- **No product code.** No Rust crate, no Python package, no Robot Framework suite, and therefore **no native rebuild**. Nothing in `crates/`, `apps/`, `src/PlatynUI` or `packages/` is touched by this change.
- **Files:** `.github/workflows/ci.yml` (one new job, only if adopted) and `dev-docs/testing-strategy.md` (§6 CI and §8 Decisions — the decision and what stays local). The spike itself lives on a throwaway branch and is not merged.
- **Depends on `atspi-process-identity`** for the artifact under test: the harness (an `#[ignore]`d integration test) and the `just` recipe that runs it belong to that change, and this change only decides where it runs. It can be researched in parallel but cannot be adopted before that recipe exists.
- **Platforms/providers:** Linux only, and only the AT-SPI2 provider's identity behaviour plus the Wayland compositor's peer handling. Windows (UIA) and macOS (AX) are untouched; the mock lane is untouched. Per `README.md`'s support table, Linux X11/AT-SPI2 and the PlatynUI compositor are the supported real backends this concerns.
- **Existing CI unchanged.** The existing jobs keep their runners, and an adopted job joins the Linux jobs on `ubuntu-latest`. The announced move of that label to 26.04 changes their stock bus, not their results, because application and runtime share a PID namespace in every existing lane.
- **No BREAKING change.** Nothing users observe changes; the worst case of the "no" outcome is documented status quo.
- **Cost:** the spike is bounded (one job, a handful of runs on a branch). If adopted, the job adds its measured wall time to every PR; if that turns out to exceed the single-digit-minute bar, the answer is "no" by the same decision rule.
- **Commit credit:** no `Co-authored-by` trailer. The credit for PR #5's author is scoped to changes 1–4 (maintainer decision), and this change contains none of that work.
