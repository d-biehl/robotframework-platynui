# Design

## Context

See proposal.md (Why) for the defect and the measurements. What follows is the state the design has to fit into. Each fact is marked **verified** (read in the code or in a dependency's source) or **measured** (observed in the podman/`unshare`/VM investigation) — nothing here is assumed unless it says so.

**Where the comparison lives today.** The provider caches `std::process::id()` once (`crates/provider-atspi/src/lib.rs:40`) and compares daemon-reported PIDs against it in three places:

| site | what it does | file:line |
|---|---|---|
| registry walk | drops an application when its PID equals ours | `lib.rs:212-224` |
| hit-test guard | returns nothing when the hit window's PID equals ours | `lib.rs:314-318` |
| popup watcher | ignores a popup candidate whose PID equals ours | `popups.rs:306-317` |

**Verified.** The PID itself is fetched with `GetConnectionUnixProcessID` at five separate call sites: `lib.rs:217` (registry walk), `lib.rs:364-367` (`application_for_pid`, the hit-test's window → application correlation), `node.rs:222-232` (`AtspiNode::resolve_process_id`, cached in `cached_process_id`), `node.rs:1404-1412` (the extents resolver's uncached copy) and `popups.rs:363-371`. **Verified.**

**What the PID is used for besides filtering.** `node.rs:1045` resolves it once per application node, and `node.rs:1175-1181` emits `control:ProcessId` plus the six `app:*` attributes only when that `Option` is `Some` — one number gates all seven, so "no PID" already means "no attributes", and the whole `app:*` block reads the local process table through `sysinfo` with that number (`process.rs`). `UiNode::id()` prefers it for an `Application` node (`node.rs:262-271`). `node.rs:1394-1398` passes it to the window manager's popup query, which keeps the compositor's popups whose client PID equals it (`crates/platform-linux-wayland/src/window_manager/platynui_ipc.rs:184-200`). The window managers also read it back: the X11 backend and the compositor backend resolve an application node's window by taking `control:ProcessId` from the node or its nearest ancestor that carries one (`crates/platform-linux-x11/src/window_manager.rs:370-415`, `crates/platform-linux-wayland/src/window_manager/platynui_ipc.rs:415-461`) and matching it against `_NET_WM_PID` or the compositor's client PID. The reverse direction, the hit-test's `application_for_pid` (`lib.rs:339-379`), matches a window's PID against the daemon's number. **Verified.** Under a cross-namespace collision that number equals the *runtime's own* PID, so everything that feeds it into the runtime's own process table describes the wrong process — **measured**, down to `@app:ProcessName = "platynui-cli-rs-pr5"` and a decoy's command line.

**Where `@ProcessId` lives, and why it stays there.** The attribute name is `attribute_names::application::PROCESS_ID` (`crates/core/src/ui/attributes.rs:127`). AT-SPI emits it in the control namespace on the `app:Application` node (`node.rs:1695-1705`), and so does UIA (`crates/provider-windows-uia/src/node.rs:1319-1331`); that is why BareMetal documents `Set Root  /app:Application[@ProcessId=${pid}]` without a prefix (`src/PlatynUI/BareMetal/__init__.py:724`). **Verified.** It is the cross-provider place for an application's identity, and this change keeps it there.

**How the missing PID actually shows up in the attributes, per daemon.** **Measured** in a podman pod with three GTK applications on one bus, one of which the daemon can resolve for us and two of which live in namespaces it cannot see: on dbus-daemon 1.14.10 and on dbus-broker 37 the unresolvable applications carry a numeric `@ProcessId = 0`; on dbus-daemon 1.16.2 the attribute is absent and the whole `app:*` block with it. Two further observations from the same run shape the attribute rule below:

- **One attribute does not go missing, it lies.** `process::query_architecture` (`process.rs:142-151`) falls back to `std::env::consts::ARCH` when it cannot read the target's ELF header, so an unresolvable application reports the *automation host's* architecture — `@app:Architecture = "x64"` for a process the runtime cannot see at all. It is the only attribute in the block that substitutes a plausible value instead of answering nothing. One layer up the attribute types add stand-ins of their own for a value they could not read — `""` for name, path, user and start time, a null for the command line, and `"unknown"` for the architecture (`node.rs:1714-1826`, **verified**) — so removing the `query_architecture` fallback alone would turn `"x64"` into `"unknown"`, not into an absent attribute.
- **A reported PID is not a readable one.** Even for the application the daemon *could* resolve, every `app:*` value came back empty, because the number the daemon reported is the application's own and the runtime cannot read that process's `/proc` from a sibling namespace. A present `@ProcessId` therefore promises nothing about the process-table block — which is exactly the split D3 makes.

**What `@Id` is, and what `UiNode::id()` is.** Two different things share the word. The XPath attribute `@Id` is resolved by `resolve_id` (`node.rs:680-687`, cached at `node.rs:1463`, surfaced at `node.rs:1552`) and is the toolkit's `Accessible.AccessibleId`, with an `accessible-id`/`id` entry of the object's attribute set as fallback: it is set when the toolkit provides one and empty when it does not — as with the three GTK3 test applications measured here, whose application root sets no accessible-id. **Verified** in the code, **measured** for those applications. It is unrelated to AT-SPI's `Application.Id`, and XPath never calls `UiNode::id()`. `UiNode::id()` (`node.rs:262-271`) is a separate accessor: for an `Application` node it prefers the process ID and otherwise returns the same accessible-id, and it surfaces as Python's `element.id` and the BareMetal `${el.id}`. Because it takes the daemon's number unfiltered, it reads `"0"` for every application the daemon cannot tell about on dbus-daemon ≤ 1.14 and on dbus-broker — two distinct applications sharing one identifier — and falls back to the accessible-id on dbus-daemon 1.16.2. **Verified**, the `"0"` **measured** as `@ProcessId = 0` on those daemons. A divergence worth flagging rather than fixing here: the core trait documents `id()` as the developer-provided identifier (`control:Id`, `crates/core/src/ui/node.rs:19-23`), which the AT-SPI `Application` override does not follow today and will not follow under D7 either. `@RuntimeId` is a third thing — the provider-dependent identifier PlatynUI uses internally to address an instance at runtime — and this change does not touch it.

**What the daemon answers for a peer it cannot see.** **Measured**, at protocol level, on seven distributions:

| implementation | `ProcessID` in credentials | `GetConnectionUnixProcessID` | `ProcessFD` |
|---|---|---|---|
| dbus-daemon 1.12 / 1.14 | present, `0` | `0` | absent |
| dbus-broker 29 / 33 | present, `0` | `0` | absent |
| dbus-broker 35 / 37 | omitted | success, `0` | present |
| dbus-daemon ≥ 1.15.10 (1.16.2) | omitted | `Error.UnixProcessIdUnknown` | present |

The bottom two rows are why the design reads `GetConnectionCredentials` rather than `GetConnectionUnixProcessID`: the credentials dictionary *omits* what it cannot answer, while the dedicated call still returns a successful `0` on dbus-broker up to its newest version.

**Three connections, not one.** The provider holds its synchronous connection (`lib.rs:120-141`), and the popup watcher opens two more — one for the event stream, one for queries — on purpose (`popups.rs:204-205`). Each has its own unique bus name, so "once per connection" means two to three decisions per process, not one. **Verified.**

**Caching today.** `node.rs:80` caches the per-node PID in a `ClearableCell`, cleared on shutdown (`node.rs:410`); `popups.rs:256` keeps a `HashMap<String, Option<u32>>` for the watcher's lifetime. Both memoize a failed lookup as `None` and never retry it. **Verified.** Every D-Bus call in the crate is bounded by `block_on_timeout_call` at 1 s (`timeout.rs:22`), so a failed lookup is a routine event, not an exotic one.

**What the decision needs, and what it does not.** The credentials of our own connection carry everything the decision uses: the `ProcessID` the daemon reports for that connection, compared once with `getpid()`. No syscall, no `/proc` read, no file descriptor and no new dependency — which is why the measured matrix above is a unit test rather than an environment. `zbus::fdo::ConnectionCredentials` models the field as `process_id() -> Option<u32>` and `DBusProxy::get_connection_credentials(bus_name)` is on the proxy (zbus 5.14.0, `src/fdo/dbus.rs:154-320`). **Verified in the dependency's source.** The same call also offers a process *file descriptor*, which would identify a process across namespace boundaries; D1 records why this change does not take it.

## Goals / Non-Goals

**Goals:**
- One decision, taken from what the daemon knows about *our own* connection, that every own-process check over a **bus peer** consults — and no own-process check anywhere else in the crate, because a window's reported process is the window system's question to answer (D10).
- Never mistake a foreign application for our own — that loss is silent and unrecoverable for the user. Failing the other way (not recognising ourselves) is visible and harmless.
- No PID is compared with a PID from another namespace, and no PID reaches `/proc` unless it is valid in the runtime's own namespace. Reporting a PID as an attribute is not a comparison: `@ProcessId` carries the application's PID as the application's own environment knows it (D3, D7).
- The decision and its inputs are legible in a log, because every degradation in this area is otherwise invisible.
- The decision is a pure function of injected inputs, so the whole measured matrix is a unit test and needs no bus.

**Non-Goals:**
- A general process-identity model for the runtime (pidfd handles threaded through the core, a fixture-process abstraction). Rejected as disproportionate: the question is local to one provider's own-process filter.
- Making the point hit-test work for an application the bus daemon cannot see at all. Its window → application step needs the number the daemon reports for the application, which the daemon does not have for such an application (spec: *Correlating a native window to an application needs a process ID both sides can express*); the spec records that as a limitation rather than a gap to close. An application co-located with the daemon is a different case: the display server and the daemon number it identically, so the correlation keeps working there as it does today (D3) — **measured** by `x11-window-owner-identity` in the sidecar pod, where runs at non-colliding PIDs resolved the target button on main.
- A new configuration key. The mode is decided from what the daemon offers; there is nothing for a user to choose.
- Anything outside `crates/provider-atspi`. The compositor's peer-credential abort, Wayland capability detection, the X11 `window_at_point` self-skip and CI adoption are the four sibling changes.

## Decisions

### D1: One decision per bus connection, taken from our own credentials

On first use of a connection the provider asks the daemon for `GetConnectionCredentials` of that connection's own unique name and compares the `ProcessID` it reports for us with `getpid()`. Equal means **local numbering**: the daemon's numbers are values in our namespace, so a peer is ours exactly when the number reported for it equals ours, and that same number is the one `/proc` may be read with (D3). Anything else — no `ProcessID`, a `0`, a number that is not ours — means **no identity**: no own-process check runs at all, and no reported number is treated as valid in our namespace.

Asking about *our own* connection is what makes this safe, and it is the whole mechanism. A peer's number on its own says nothing: a `0` from a daemon that cannot see that peer looks exactly like a `0` from a daemon that cannot see anybody, and a real number from a daemon in an ancestor namespace belongs to somebody else. Checking the one number we can verify turns the question into a single comparison whose answer cannot be wrong, rather than into a chain of tests that each have to be right.

*Alternatives considered:*
- **PR #5: resolve our own PID through `GetConnectionUnixProcessID` and compare both sides.** Rejected on measurement, not on taste. dbus-daemon ≤ 1.14 and dbus-broker at every version up to 37 answer that call with a successful `0` for an invisible peer, so both sides are `Some(0)` and every other invisible application is discarded — 58 false positives against main's 27 over the whole matrix, and a second real GTK application dropped with no PID collision present. It is safe only on dbus-daemon ≥ 1.15.10.
- **Drop own-process filtering entirely.** Rejected. On an ordinary desktop the filter does real work — the Inspector must not show or pick its own window — and that case is exactly the one where identity is cheap and reliable.
- **Compare unique bus names instead of processes.** Rejected: it recognises only our *own* connection, not our process. The Inspector's accessible application is registered by a different connection than the provider's, so the filter would stop excluding it.
- **Identify the process by a namespace-independent handle — the daemon's `ProcessFD`.** Measured at length and **not taken; settled with the maintainer, who asked for the simplest rule that cannot be wrong.** A pidfd names a process across namespace boundaries, so it would recognise our own connection even where the number answer disappears — the sidecar topology. What it costs is why it is out. The inode comparison needs an `fstatfs` check that the descriptor lives on `pidfs`, because on kernel 6.8 — Ubuntu 24.04's GA kernel, whose at-spi2-core 2.52 prefers dbus-broker — every pidfd is an `anon_inode` with `st_ino = 69`, one inode for all processes: the self-test then passes for *every* peer and the provider claims every application as its own, an empty tree on a stock desktop (**measured** in a VM). Avoiding that needs a second branch reading the peer's PID in our namespace from `/proc/self/fdinfo/<fd>`, and with it a descriptor lifetime to manage on the per-application enumeration path (**measured**: every credentials reply hands out a descriptor that stays open until the value is dropped). Against that, what it buys in the topology this capability supports is close to nothing: a runtime in a sidecar has no user interface on the application's display, so it has nothing of its own to hide, and the local PID a descriptor would translate to is `0` for a peer in a sibling namespace — **measured** — so the `app:*` block stays absent either way. Only a runtime in an *ancestor* namespace would gain a local PID, and that is not the supported topology. Recorded here as the extension to reach for if the runtime ever does need to recognise itself across a namespace boundary.

### D2 and D4: withdrawn

Both described the process-descriptor chain — the `pidfs` filesystem-magic check that guarded the inode comparison, and the translated-descriptor branch beneath it. The chain is not taken (D1, last alternative), so both decisions are gone rather than renumbered: every other decision keeps the number the rest of this change, the spec deltas and the sibling changes refer to it by.

### D3: One number per application, and one verdict about whether it is ours to use

Across a namespace boundary an application's process ID is a number in *its* environment, not in ours. The provider therefore keeps one number and one verdict — not two numbers. In a shared namespace the distinction collapses, which is why an ordinary desktop sees no change.

The **number** is the `ProcessID` the bus daemon reports in the credentials of the application's connection — the PID as the application's own environment knows it; in the Kubernetes shape, what `ps` shows inside the application container. It is the application's identity: `@ProcessId` (D7) and, through it, the window managers' node → window lookup; `UiNode::id()` (D7); the popup query `wm.popups(pid)` (`node.rs:1394-1398`); and the hit-test's window → application step (`application_for_pid`, D5). It is taken as reported, in both outcomes, whether or not it is valid in the runtime's namespace. It is **absent** when the daemon cannot tell — `ProcessID` omitted, or present as `0` — and when the lookup fails; it is **never `0`**. For a peer the daemon cannot see, that covers the three measured daemon behaviours of the Context table: `ProcessID` present as `0` (dbus-daemon 1.12/1.14, dbus-broker 29/33), omitted where the legacy call would answer a successful `0` (dbus-broker 35/37), and omitted where the legacy call would answer `UnixProcessIdUnknown` (dbus-daemon ≥ 1.15.10).

The **verdict** is D1's outcome, and it decides whether that number may reach `/proc`. Under **local numbering** the daemon numbers processes as we do, so the reported number is also the local PID and the `app:*` block may be read with it. Under **no identity** there is no locally valid process ID for any application on that bus, so the block is absent. Nothing else derives one: no descriptor, no `/proc/self/fdinfo`, no second source. Not to be confused with the identity itself: the verdict is about a *numbering space*, the number is a value reported to the user.

Neither is ever compared across namespaces. The own-process decision compares the daemon's numbers with `getpid()` only under local numbering, where the self-check has shown that both live in the runtime's namespace (D1). The other consumers of the reported number — the X11 backend matching `@ProcessId` against `_NET_WM_PID`, the compositor backend and `wm.popups(pid)` matching it against the compositor's client PID, `application_for_pid` matching it against the window's PID — compare it with a number the display server reports for the same application, and the `sidecar-deployment` topology requires the display server and the bus daemon to live in the application's namespace, so both sides number the application identically. A deployment that splits them is outside that topology. The the reported number and the local PID are never compared with each other, and reporting the reported number as `@ProcessId` is not a comparison at all.

*Alternatives considered:*
- **Read `/proc` with the reported number whatever the verdict.** Rejected: that is the measured collision defect — in a foreign namespace the number names a different local process or none, and the application was reported with the automation binary's own name and a decoy's command line. On dbus-broker 37 the credentials omit `ProcessID` for an invisible peer while the legacy call still answers `0`, and on a same-uid ancestor-namespace daemon the number would be real but foreign; neither is a number for `/proc`.
- **Emit `@ProcessId` only where the number is locally valid.** Rejected; see D7.

### D5: One helper, one round trip, replacing five call sites

All five `GetConnectionUnixProcessID` calls become one helper that takes a bus name and returns the peer's classification (ours / not ours / unknown) together with the number the daemon reported for it (D3), from a single `GetConnectionCredentials` round trip. The attribute path (`node.rs:222`, feeding `node.rs:1045` and `UiNode::id()`) takes that number for `@ProcessId` and `id()`, and — only under local numbering, where it is locally valid — the same number for the `app:*` block. The popup query's copy (`node.rs:1404`) takes the reported number, because the compositor numbers its clients in the application's namespace. The two bus-side filters (`lib.rs:217`, `popups.rs:367`) take the classification. `application_for_pid` (`lib.rs:364`) compares the window's PID with the reported number and skips when either is absent — which keeps today's correlation for every application the daemon can tell about and stops matching on the `0` the older daemons report for the rest.

*Alternatives considered:*
- **Keep the legacy call for the PID and add credentials only for identity.** Rejected: it doubles the round trips per application on the hot enumeration path, and keeps the call whose `0` caused the problem.

### D6: Cache definitive answers, retry transient ones

Per connection, a map from unique bus name to the daemon's definitive answer — the reported number, not the verdict drawn from it: a peer can be asked about while the connection's own decision is still pending after a transient failure, and a verdict stored then would outlive it. Definitive means the daemon answered — with a number, or with "no such connection"/credentials that contain nothing usable. A timeout (1 s, `timeout.rs:22`), an I/O error, a closed connection, or a daemon out of memory or over a quota are not answers and are not stored. `shutdown()` clears the maps of the provider's own connections, like `node.rs:410` clears the per-node cell today — only those: a process can hold several runtimes, each bound to a bus of its own (`providers.atspi.bus_address`), and their state is theirs. For the same reason a connection is keyed by the bus instance it is connected to (the daemon's GUID) together with its unique name, because unique names repeat across buses. The per-connection outcome of D1 follows the same rule: a failed decision is retried on the next query rather than freezing the connection into no identity.

*Alternatives considered:*
- **Cache `Option<u32>` as today (`popups.rs:256`).** Rejected: that is PR #5's second defect and the watcher's existing one — one slow reply mislabels an application for the rest of the connection's life.
- **Time-based expiry.** Rejected as unnecessary: a unique bus name is never reused on one bus, so a definitive answer about one cannot go stale.

### D7: Absent beats zero, and absent beats a plausible guess

**Settled by the maintainer.** An application's identity is `@ProcessId` on the `app:Application` node, and it carries the number the daemon reports (D3): reported whenever the daemon gives a non-zero `ProcessID` for the application's connection, whether or not that number is valid in the runtime's namespace, **absent** otherwise and **never `0`**. The six `app:*` process-table attributes are read only through a process ID valid in the runtime's namespace — the same number, under local numbering (D3) — and are absent under *no identity*. Today `node.rs:1175-1181` gates all seven attributes on one `Option`; the implementation splits that gate in two, the attribute from the number and the block from the verdict. The two are independent: in the sidecar the normal picture is a present `@ProcessId` with an absent `app:*` block, and the presence of one says nothing about the other.

`UiNode::id()` (`node.rs:262-271`) uses the same value as `@ProcessId` — the reported number as a decimal string — and without one falls back to what it returns today without a PID, the accessible-id from `resolve_id`. It never reads `"0"`. The XPath attribute `@Id` stays the toolkit accessible-id (Context), and `@RuntimeId` is untouched: it is the provider-dependent identifier PlatynUI uses internally to address an instance at runtime, and nothing in this change reads, changes or publishes it as a handle.

Three rules, because the measurement forced them apart:

1. **Not determinable means absent, never substituted.** `app:Architecture` is today the one attribute that answers with something rather than nothing: `process::query_architecture` (`process.rs:142-151`) falls back to `std::env::consts::ARCH`, so an unresolvable application reports the automation host's architecture — **measured** as `x64` for a process the runtime cannot even see. That fallback goes, and **the maintainer decided that the attribute goes with it**: the AT-SPI provider reports no architecture. Linux keeps no architecture per process: `/proc/<pid>/status` has no such field, `personality` is not one, and the platform string in the auxiliary vector lives in the process's memory, which Yama's default `ptrace_scope` keeps from a non-parent (**measured**). The only source left is the executable's ELF header, and it is a poor one. It needs a hand-kept table of machine types that is incomplete by nature, since `e_machine` `0xF3` names 32- and 64-bit RISC-V alike. Its meaning is fuzzy: a script reports its interpreter. And read through the resolved executable path, it is not even the process's own file for an application in a container of its own — **measured** with a bind-mounted executable in a mount namespace of its own, where the runtime's file under the same name answered a plausible wrong architecture. Nothing in PlatynUI consumes the value on Linux: AT-SPI is IPC, and the Java attach on Unix goes through a socket, independent of the target's architecture. With the fallback go the attribute layer's stand-ins for a value it could not read (`""`, a null, `"unknown"`, `node.rs:1714-1826`); an attribute whose value cannot be determined is absent. The same rule is why `@ProcessId` is absent rather than `0`. The maintainer confirmed that this holds on an ordinary desktop too, where it changes what a consumer sees for a process whose `/proc` entry the runtime cannot read.
2. **A locally valid number gates the process-table block, it does not fill it.** A process that is visible to the runtime can still have `/proc` entries it may not read — another user's process, a `/proc` mounted with `hidepid`; **not measured**, but nothing about a valid PID rules it out. Each `app:*` attribute is therefore reported only when it was actually read, and the spec says so rather than promising a populated block wherever a local PID exists.
3. **Reporting is not comparing.** `@ProcessId` reports a number from the application's namespace without the provider ever comparing it with its own PID or feeding it into `/proc`. Its consumers — the window managers' node → window lookup, `wm.popups(pid)`, `application_for_pid` — compare it only with numbers the display server reports for the same application, which the `sidecar-deployment` topology places in the same namespace (D3).

This is deliberately a behaviour change on dbus-daemon ≤ 1.14 and dbus-broker in the sidecar topology, where applications the daemon cannot tell about report `@ProcessId = 0` today and their `UiNode::id()` reads `"0"` for all of them alike — **measured**. A shared identifier across distinct applications is worse than a missing one: a consumer that keys on it silently addresses the wrong node, and the X11 backend's `pid_from_attr` (`crates/platform-linux-x11/src/window_manager.rs:404-415`) accepts an integer `0` and would look windows up by it. Where the daemon *does* know the application's PID — every application co-located with it — `@ProcessId` keeps reporting exactly what it reports today; what goes is the `app:*` block that today describes whatever local process happens to carry that number.

*Alternatives considered:*
- **Report `0` and document it.** Rejected: `0` is a valid-looking number that flows into `/proc` lookups, window lookups and XPath comparisons.
- **Report the host's architecture and document it as best effort.** Rejected: it is indistinguishable from a real answer, and on a foreign-architecture container it is simply false.
- **Read the architecture from the ELF header through `/proc/<pid>/exe`.** Implemented and measured correct in every topology, then dropped by the maintainer: it keeps a hand-kept machine table and a binary-format parser for a value nothing on Linux consumes, and whose meaning is unclear for scripts and emulators.
- **Emit `@ProcessId` only where the number is locally valid** (this change's earlier rule). Rejected by the maintainer's decision. In the sidecar it would drop the attribute for every application, although the daemon knows each one's PID and `ps` in the application container shows exactly that number. It would also break the correlations that read the attribute back: the X11 and compositor backends compare it with `_NET_WM_PID` or the compositor's client PID, which are application-namespace numbers, so a local PID would find no window there, and `application_for_pid` would stop resolving the co-located application that main resolves today.
- **Fall back to the unique bus name for the node identifier.** Dropped: the bus name is part of `@RuntimeId`, which stays untouched, and `UiNode::id()` keeps what it returns today without a PID.

### D8: One log line per connection, and a warning when identity is lost

At `info` level, once per connection: the outcome, the `ProcessID` the daemon reported for our own connection (or that it reported none), and `getpid()`. When the outcome is no identity, a `warn` stating that own-process exclusion is inactive for that connection.

Two numbers and a verdict are the whole record, and that is the point: anybody reading it can redo the decision. The `warn` is what makes the degradation findable in a deployment where it was not expected — a bus that stopped numbering us after a topology change shows up as one line at start-up instead of as filtering that quietly stopped. On an ordinary desktop the outcome is local numbering and nothing warns.

### D9: A pure decision function plus a local namespace harness

The per-connection decision, the peer classification and the number a peer carries (D3) take injected inputs — the reported `ProcessID` for our own connection, the reported `ProcessID` for the peer, our own PID — and so does the choice of what an application node reports (`@ProcessId`, the `app:*` gate, `UiNode::id()`, D7). The entire measured matrix, including the three daemon behaviours for a peer the daemon cannot see, becomes table-driven unit tests with no bus, no container and no root. Everything that cannot be injected (that a real daemon behaves as measured; that the chain survives a real collision) goes into an `#[ignore]`d test driving several PID namespaces with `unshare` — a module inside the crate (`src/pidns_harness.rs`), because the identity helper it asserts is private to the crate — — the supported arrangement, the one where the daemon shares the runtime's namespace but not the application's, and the forced collision — behind a `just` recipe — the shape `crates/java-agent/tests/live_fixture.rs` and `just test-java-agent-live` already establish for "needs a real thing, not in the default lane".

That shape includes its prerequisite rule, which the maintainer has made the convention for every namespace test in this series: a missing prerequisite **fails the run loudly**, naming what is missing, and never skips silently — `live_fixture.rs`'s module docs and the notes above both `test-java-agent-live` recipes in the `justfile` say the same for the Java fixtures. For this harness the prerequisites are `unshare` with unprivileged user namespaces permitted (the AppArmor restriction on stock Ubuntu noble blocks them, see below) and the bus daemon a run is asked to use. The daemon is a **parameter** of the run (`dbus-daemon` or `dbus-broker`), not a list that must be installed in full: each run fails loudly when *its* daemon is missing, and nobody needs both installed to run the harness at all. Covering both implementations means running it once per daemon. A green run therefore always means the namespace cells for that daemon actually ran.

Two further properties are what `evaluate-pidns-tests-in-ci` requires before any harness in this series may run in CI (its D7), and this harness is built with them from the start. The forced collision takes its PID before anything else starts in the probe's namespace, with a bounded retry, and a collision that did not take effect fails the run — otherwise the most important topology could pass without having been set up. And every run names, per topology, the daemon binary and its version, the decided outcome and its inputs, so its output says what was actually exercised.

*Alternatives considered:*
- **A podman-pod matrix as the repeatable test.** Rejected for this change: ~1 GB of images and a display server to reproduce answers that two `unshare` calls and one socket directory produce identically — **measured**, the harness yielded the same mode decisions and the same verdicts as the whole pod matrix. The pod images stay a local research tool.
- **Wiring the harness into CI now.** Deferred to `evaluate-pidns-tests-in-ci`, which still has open research (the AppArmor sysctl for unprivileged user namespaces was measured to block `unshare -Ur` on stock noble, but never on a hosted runner).

### D10: The hit-test guard is removed — the window system decides ownership, the provider does not re-derive it

**Settled.** `lib.rs:314-318` is deleted, and with it `SELF_PID` (`lib.rs:40`). The provider stops deciding window ownership altogether. It still reads its own PID in one place, the identity module's self-test (D1, D4), and compares it there only with numbers the kernel or the daemon expressed in its own namespace — never with a number a window reported.

**Ordering, settled with the maintainer: the deletion depends on `fix-compositor-foreign-pidns-clients`.** Measured in the podman pod, the compositor's `window_at_point` returns the caller's own window and excludes nothing; today the guard turns that answer into *no element*. Deleting the guard before the compositor skips the caller's windows would let the Inspector's picker select the Inspector's own window under the PlatynUI compositor — a regression, not an accepted loss. X11 has no such dependency: its window manager already skips an own window today and resolves the one behind it, and `x11-window-owner-identity` changes only how that ownership is established.

The value the guard compared is **not** a bus peer: `hit.pid` is the window's `_NET_WM_PID`, a number the X11 client wrote from *its* `getpid()`, handed up by `crates/platform-linux-x11/src/window_manager.rs`. The identity decision says nothing about it: the self-check shows that the *bus daemon's* numbering is ours, never that the *display server's* is. So the guard could never have consulted that decision; it could only have kept comparing a number whose namespace it does not know.

Both window systems now answer the ownership question where the evidence actually lives, so a hit that reaches the provider has already passed an ownership decision:

- **X11** — `x11-window-owner-identity` makes `window_at_point` skip an own-process window only when the display server confirms via XRes that its view of our connection carries the number we know ourselves by, and never otherwise.
- **Wayland** — the PlatynUI compositor skips the caller's own windows in its own `window_at_point` (`fix-compositor-foreign-pidns-clients`). It is the only party that sees both the requesting client and the surface, so it is the only one that can decide this under the compositor.

Re-checking the same client-reported number one layer up could only undo those decisions — which is exactly the defect in the sidecar topology, where the number means nothing to us. Under a forced collision the hit-test returned "No element" on main *and* on PR #5 — **measured** — because the window was dropped twice; removing this guard is what makes the window-system fix observable end to end.

The spec requirement *Own-process exclusion is applied consistently wherever the provider hides its own UI* is written accordingly: the provider applies one identity decision to **bus** peers, and defers the window-system half to `element-at-point`.

## Risks / Trade-offs

- **The `app:Architecture` fallback is a substituted value, not a missing one** → It is the only attribute in the block that answers when it cannot read the target, and on a foreign-architecture container its answer is simply wrong. D7 removes the attribute from the AT-SPI provider altogether, and the attribute layer's `""`/null/`"unknown"` stand-ins for the rest of the block; the risk of the removal is that a consumer relying on an attribute always being present now sees it absent — which is the same class of change as the rest of the block, and preferable to a confident wrong answer. No consumer in the repository reads `app:Architecture`.
- **Own-process filtering is off in no-identity mode, so the runtime's own application can show up in its own tree** → Accepted and specified. It is visible (the application is *there*, with its own name) and recoverable by a locator; the failure it replaces — a foreign application silently missing — is neither.
- **A daemon in an *ancestor* namespace could report a translated PID that coincidentally equals `getpid()`, selecting local numbering wrongly** → **Not measured**; theoretical. Unreachable in the topologies we care about, because a parent-namespace PID is large while a fresh child namespace starts at 1 — the same asymmetry that makes the reported bug need "bus and application inside one container". Left as a known residual rather than defended against.
- **Own-process recognition is gone across every namespace boundary, not only where it was already impossible** → The cost of the simple rule, accepted with it: a runtime that does have a user interface on the application's display *and* runs in another namespace shows that interface in its own tree. Measured to be the sidecar's normal state anyway with the daemons that omit the number; the descriptor chain D1 rejects is the extension that would restore it.
- **Behaviour change for anything keying off `@ProcessId` of an application the daemon cannot tell about** → It goes from `0` to absent. Only reachable in a deployment that is broken today; on dbus-daemon 1.16 the attribute is already absent, so consumers cannot have depended on it across bus implementations.
- **In the sidecar, `@ProcessId` is a number the runtime cannot use locally** → A consumer that feeds it into the runtime's own process table (`psutil`, `/proc`, `kill`) reaches a different process or none. Accepted and specified: the attribute is the application's identity as its own environment knows it, and what the runtime can say about the process locally is what the `app:*` block answers — or declines to. The correlations that consume it inside PlatynUI are consistent only under the co-location prerequisite of `sidecar-deployment` (display server and bus daemon in the application's namespace); a deployment that splits the two is outside the supported topology.

## Migration Plan

Behavioural within one crate, additive at every boundary: no trait, no attribute name, no configuration key, no Python or Robot Framework surface changes. A native rebuild (`just build-native`) is needed before a Python/RF lane sees it, and the CLI and Inspector pick it up with their own builds.

**Position in the series:** this is change 2 of five and is implemented after `fix-compositor-foreign-pidns-clients`. The two share no code, but the order is a dependency: deleting the provider's hit-test guard (D10) is safe under the PlatynUI compositor only once the compositor skips the caller's own windows itself. `x11-window-owner-identity` (change 4) depends on this change for the *end-to-end* hit-test observation (D10), and `evaluate-pidns-tests-in-ci` (change 5) depends on the `unshare` harness and its `just` recipe that this change builds.

Rollout order inside the change: the decision function and its unit tests → wire the two bus-side filter sites, remove the hit-test guard (only once `fix-compositor-foreign-pidns-clients` has landed), and split the attribute path into the reported number and the verdict → the `unshare` harness. The X11 and compositor acceptance lanes are the regression gate for the ordinary desktop; there the daemon numbers us as we number ourselves, so the outcome is local numbering and the behaviour is today's — those lanes should not move.

Rollback is a revert of the commit. No state, no configuration and no on-disk format is introduced that would survive it. A rollback switch of the `providers.atspi.surface_popups` kind (`lib.rs:71-73`) was considered and not adopted: the mode is not a user choice but a fact about the bus, and a switch that forces the old comparison would only re-enable a defect.

## Open Questions

1. **Settled, recorded for the reader: `element-at-point`'s MODIFIED delta lives in change 4.** Its requirement *Hit-test excludes the host process's own UI* was unconditional, and in no-identity mode it no longer holds. Two changes rewriting one requirement text would produce contradicting deltas, so this change writes none and specifies the provider-side behaviour in `sidecar-deployment` instead; `x11-window-owner-identity` publishes the single delta and its text makes the guarantee conditional on ownership being establishable, referring the provider-side guard back here. Nothing is left for the maintainer unless he wants the two halves folded into one follow-up capability.
2. **Settled, recorded for the reader: an application's identity is `@ProcessId`.** It stays on the `app:Application` node where both providers already emit it, and it reports the number the bus daemon gives for the application's connection — the PID as the application's own environment knows it — absent when the daemon cannot tell and never `0` (D3, D7). `@Id` stays the toolkit accessible-id, set when the toolkit provides one and empty when it does not (Context). `@RuntimeId` is the provider-dependent identifier PlatynUI uses internally to address an instance at runtime; this change does not touch it and does not offer it as a user-facing handle. `UiNode::id()` follows `@ProcessId` and falls back to the accessible-id (D7).
3. **Settled, and settled against the descriptor chain.** The maintainer asked for the simplest rule that cannot be wrong: one question per connection — does the daemon number us as we number ourselves — and where the answer is no, the behaviour and the attributes that depend on it are unavailable. D1's last alternative records the chain that was measured and not taken, and what it would have bought; D2 and D4, which described it, are withdrawn.
4. **Settled, recorded for the reader: the provider-side hit-test guard at `lib.rs:314-318` is removed (D10).** Its input is an `_NET_WM_PID`, which no identity mode can speak about, so "one decision everywhere" could never have meant "consult the mode here". The decision taken is that the provider stops deciding window ownership at all: on X11 the window manager decides via XRes (`x11-window-owner-identity`), and under the PlatynUI compositor the compositor skips the caller's own windows in its own `window_at_point` (`fix-compositor-foreign-pidns-clients`). Task 4.2a removes the guard and `SELF_PID`, and only after `fix-compositor-foreign-pidns-clients` has landed (D10, ordering); `x11-window-owner-identity`'s task 5.1 is the run that observes the two layers agreeing end to end, and its own Open Question 1 is answered by this entry.
