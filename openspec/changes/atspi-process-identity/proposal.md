# Proposal

## Why

The AT-SPI provider answers "does this application belong to my own process?" by comparing a PID the bus daemon reports with `std::process::id()` (`crates/provider-atspi/src/lib.rs:40`, `:221`, `:317`, `popups.rs:315`). That comparison is only meaningful while the runtime and the a11y bus daemon share one PID namespace. PlatynUI is now expected to run in a *sidecar* deployment — the application container holds display server, a11y bus daemon and the application, the runtime runs in a sibling container without `shareProcessNamespace` — and there the daemon reports PIDs from a namespace we do not share.

The failure is not theoretical. Measured in a podman pod with the runtime forced onto the application's daemon-visible PID: `count(//*)` returns **0** with `DEBUG skipped own process app=:1.3 pid=56`, on X11 and on the PlatynUI compositor alike, against dbus-daemon 1.14.10, dbus-daemon 1.16.2 and dbus-broker 35. With `shareProcessNamespace` the whole failure class disappears. A second measured consequence: the `app:*` attributes are not merely empty but wrong — the target application reported `@app:ProcessName = "platynui-cli-rs-pr5"` (the automation binary), and with an unrelated process parked on the colliding PID, `ProcessName="python3"` with that process's command line and executable path.

External PR #5 (Fabian Tsirogiannis) reported this accurately and fixed the tree by resolving *our own* PID through the daemon instead of `getpid()`. Measurement showed its comparison is unsafe on the bus implementations most distributions ship: dbus-daemon ≤ 1.14 and dbus-broker at every version tested up to **37** answer `GetConnectionUnixProcessID` with a successful `0` for a peer they cannot see, so both sides compute `Some(0)` and any *other* invisible application is dropped as "our own". Measured without any PID collision, with a second real GTK application on the bus: main showed 2 applications, PR #5 showed 1. Over all runs, PR #5 produced 58 false positives against main's 27. The chain proposed here produced 0 in 123 container runs, 22 VM peer checks and 12 CLI runs.

## What Changes

- **New:** the provider decides, once per bus connection, how it can recognise its own process, by asking the daemon about *its own* connection:
  - **FD** — the daemon returns a process file descriptor for our connection, that fd lives on `pidfs`, and its inode equals the inode of a pidfd opened on our own PID. An application is ours exactly when the daemon returns a process fd for it with the same inode. This works *across* PID namespaces, because pidfs inodes are namespace-independent (measured).
  - **FD via the translated PID** — otherwise, if a descriptor is there but its inode is unusable (no `pidfs`), the descriptor's process is read as a PID in *our own* namespace (the `Pid:` line of `/proc/self/fdinfo/<fd>`) and compared with `getpid()`. An application is ours exactly when its descriptor carries our number here; a peer we cannot see carries none and is never ours. Measured as exact on kernel 6.8, where the inode comparison is useless.
  - **PID** — otherwise, if the daemon reports a process ID for our connection and it equals `getpid()`, daemon-reported PIDs are in our numbering space and are compared as today.
  - **OFF** — otherwise no own-process check is performed at all. Nothing is filtered; the runtime's own application may appear in its own tree. This is the accepted loss, and strictly better than today's behaviour, which mistakes a *foreign* application for our own.
  - The `pidfs` check is load-bearing for the inode comparison and is **not** replaceable by the inode self-test: on kernel 6.8 (the Ubuntu 24.04 GA kernel, whose at-spi2-core 2.52 prefers dbus-broker) every pidfd is an `anon_inode` with `st_ino = 69`, so the self-test passes for *every* peer. Without the filesystem-magic check the provider would claim 100 % of peers as its own — an empty tree on an ordinary desktop, not only in a container. That is why such a descriptor falls through to the translated PID instead of being trusted by inode.
- **Changed:** the own-process decision is applied wherever the provider filters a **bus peer**: the registry walk in `get_nodes` (`lib.rs:221`) and the popup watcher's candidate filter (`popups.rs:315`). Filtering happens only on a *positive* match; an unresolved identity never filters anything.
- **Removed:** the own-UI guard in `element_at_point` (`lib.rs:314-318`) goes, and with it `SELF_PID` (`lib.rs:40`); the only read of our own PID left in the crate is the identity module's self-test, which compares it only with numbers expressed in our own namespace. The removal **depends on `fix-compositor-foreign-pidns-clients`**: measured, the compositor's `window_at_point` returns the caller's own window today, so without that change the Inspector's picker would select itself under the PlatynUI compositor. The guard compares an `_NET_WM_PID` the window manager handed up, not a bus peer, so no identity mode can speak about it — and it is no longer needed, because **the provider stops deciding window ownership**: on X11 the window manager decides via XRes (`x11-window-owner-identity`), and under the PlatynUI compositor the compositor skips the caller's own windows in its own `window_at_point` (`fix-compositor-foreign-pidns-clients`). A hit that reaches the provider has already passed an ownership decision taken where the evidence lives; re-deriving it from a client-reported number could only undo it, which is exactly what makes the window disappear a second time under a collision.
- **Changed:** an application's process ID and its process-table data follow two separate rules, because across a PID-namespace boundary one application has **two numbers**: the PID the bus daemon reports for its connection — the *daemon-view PID*, what `ps` shows inside the application container in the Kubernetes shape — and, where the runtime can see the process at all, its PID in the runtime's own namespace — the *local PID*. The two coincide in a shared namespace.
  - **Application identity is `@ProcessId` on the `app:Application` node**, where both providers already emit it: attribute name `attribute_names::application::PROCESS_ID` (`crates/core/src/ui/attributes.rs:127`), in the control namespace on AT-SPI (`node.rs:1695-1705`) and on UIA (`crates/provider-windows-uia/src/node.rs:1319-1331`), which is why BareMetal documents `Set Root  /app:Application[@ProcessId=${pid}]` without a prefix (`src/PlatynUI/BareMetal/__init__.py:724`). It reports the **daemon-view PID** — the PID as the application's own environment knows it — whether or not that number is valid in the runtime's namespace. It is **absent** when the daemon cannot tell (`ProcessID` omitted or `0`, `UnixProcessIdUnknown`, a failed lookup), and it is **never `0`**. Measured with three GTK applications on one bus: today an application the daemon cannot tell about reports `@ProcessId = 0` on dbus-daemon 1.14.10 and dbus-broker 37, while dbus-daemon 1.16.2 omits the attribute.
  - **The six `app:*` process-table attributes** (`node.rs:1175-1181`, `process.rs`) are read only through the **local PID**, and are absent without one — never through the daemon-view PID, which in a foreign namespace names a different local process or none; that is how the automation binary's own name ended up on the application (Why). An attribute that cannot be determined is absent rather than guessed: `@app:Architecture` today does not go missing but *fabricates*, because `process::query_architecture` (`process.rs:142-151`) falls back to `std::env::consts::ARCH` and so reports the automation host's `x64` for a process the runtime cannot see. That fallback goes, and so do the attribute layer's own stand-ins for a value it could not read (`""`, a null, `"unknown"`, `node.rs:1714-1826`). Measured too: even for the application the daemon could resolve, every `app:*` value came back empty from a sibling namespace, because the reported number is the application's own and not one the runtime can read — so a present `@ProcessId` promises nothing about the `app:*` block.
  - **No PID from one namespace is ever compared with a PID from another; reporting the daemon-view PID as an attribute is not a comparison.** The comparisons that do consume it stay inside one namespace under the topology the `sidecar-deployment` spec requires, where display server and bus daemon live in the application's namespace: the X11 and compositor window managers find an application's window by matching `@ProcessId` against `_NET_WM_PID` or the compositor's client PID, `wm.popups(pid)` filters the compositor's popups by the same number, and the hit-test's window → application step (`application_for_pid`) compares the window's PID with the daemon-view PID. All three keep working in the sidecar for an application co-located with the daemon, exactly as they do on a desktop.
- **Changed:** `UiNode::id()` for an `Application` node (`node.rs:262-271`, surfaced as Python's `element.id` and the BareMetal `${el.id}`) uses the same value as `@ProcessId` — the daemon-view PID, never `0` — and without one falls back to what it returns today without a PID, the accessible-id. Today it takes the daemon's number unfiltered, so it reads `"0"` for every application the daemon cannot tell about on dbus-daemon ≤ 1.14 and dbus-broker (two applications, one identifier). This is **not** the XPath attribute `@Id`: that is the toolkit's `Accessible.AccessibleId` (`resolve_id`, `node.rs:1463`, surfaced at `node.rs:1552`), set when the toolkit provides one and empty when it does not — as with the three GTK3 test applications measured, whose application root sets none — and unrelated to AT-SPI's `Application.Id`. `@Id` stays the accessible-id. `@RuntimeId`, the provider-dependent identifier PlatynUI uses internally to address an instance at runtime, is untouched by this change.
- **Changed:** the five separate `GetConnectionUnixProcessID` calls (`lib.rs:217`, `lib.rs:366`, `node.rs:228`, `node.rs:1409`, `popups.rs:367`) are replaced by one helper over `GetConnectionCredentials`, which returns the own-process classification, the daemon-view PID *and* the local PID in one round trip.
- **Changed:** caching. Only definitive answers are cached — a resolved identity, or the daemon's explicit "I cannot tell you". Transient failures (the 1 s D-Bus timeout in `timeout.rs:22`, I/O errors) are retried, and `shutdown()` clears the cache. Today's `pid_cache` in `popups.rs:256` memoizes a transient `None` for the worker's whole lifetime; PR #5 does the same for the connection's lifetime.
- **New:** one log line per bus connection naming the chosen mode and the inputs it was chosen from, so that a silent degradation — most plausibly the zbus connection not negotiating UNIX fd passing, without which the daemon never sends a process fd — is visible in a log instead of invisible.
- Behaviour change, not breaking on a normal desktop: where the daemon can resolve PIDs (every single-namespace session) the daemon-view PID and the local PID are the same number, so the tree, the attributes, `element.id` and the filtering stay exactly as they are. The changes above are only observable where the daemon cannot see us or the application — with one small exception that applies everywhere: an `app:*` value the runtime cannot read (another user's process, say) becomes an absent attribute instead of `""`, a null or `"unknown"`.

## Capabilities

### New Capabilities

- `sidecar-deployment`: PlatynUI running in a different PID namespace than the application it automates — the supported topology and its prerequisites, what "process identity" means when PIDs are not comparable, which behaviour degrades in which way, and the rules every provider follows for PID-valued attributes — which process ID an application reports, and which one may read the process table. Written cross-provider because the same question arises for the X11 window owner (change `x11-window-owner-identity`) and the Wayland compositor's peer credentials (changes `fix-compositor-foreign-pidns-clients`, `wayland-sidecar-capabilities`); this change implements the AT-SPI part.

### Modified Capabilities

- `atspi-event-driven-tree`: the scenario "The provider's own process popups are not surfaced" is unconditional today. It holds only on a positive identity match; when identity cannot be established the watcher surfaces popups from every process, including its own.

## Impact

- **Rust — `crates/provider-atspi`** (Linux, AT-SPI2; supported per README's platform table for X11 and for the PlatynUI Wayland compositor): a new internal identity module, plus edits in `lib.rs`, `node.rs`, `popups.rs`, `process.rs` and `connection.rs` (an unreachable bus names its address in the error). New direct use of `zbus::fdo::DBusProxy::get_connection_credentials` (`zbus` 5 is already a dependency and `ConnectionCredentials::process_fd()` is already exposed) and of rustix's safe `pidfd_open`, `getpid`, `fstat` and `fstatfs` — a direct `rustix` dependency with the `fs` and `process` features, the same `rustix` 1.1.4 already in the lock — so the identity module needs no `unsafe`. No new crate enters the lock.
- **Rust — no core or trait change.** `UiTreeProvider`, `WindowManager` and the attribute constants stay as they are, so no other provider or platform crate is touched. `crates/provider-windows-uia`, `crates/provider-java*`, `crates/provider-mock` and the macOS stub are unaffected — the mock has no bus and no PIDs to compare.
- **Consumers of the crate:** `packages/native` and `crates/cli` link the provider (`packages/native/Cargo.toml:44`, `crates/cli/Cargo.toml:49`). A **native rebuild** (`just build-native`) is needed before any Python/RF lane sees the change; the Inspector and the CLI pick it up with their own builds.
- **Python / Robot Framework:** no API, keyword or docstring change. The `PlatynUI` library surface, the BareMetal keywords and `packages/native`'s bindings are untouched; BareMetal's documented `/app:Application[@ProcessId=${pid}]` keeps its meaning wherever the runtime and the application share a PID namespace — which is every desktop lane. Across a namespace boundary the attribute is the application's own number rather than one the caller can obtain locally, and where the daemon can resolve no peer it is absent, so such a locator matches nothing (`sidecar-deployment`). An AT-SPI application's `element.id` changes only where it read `"0"`. The mock lane (`just test-python`, `tests/BareMetal`) is unaffected by construction.
- **Tests:**
  - Rust unit tests in `crates/provider-atspi` for the mode-decision table (every measured bus/kernel row, the kernel-6.8 `anon_inode` trap via an injected filesystem magic, self-test mismatch, "0 is never an identity"), for peer classification, for the caching rule, for the attribute split (`@ProcessId` reported from the daemon-view PID although it is not locally valid; absent and never `0` on each of the three measured daemon behaviours for a peer the daemon cannot see; `app:*` absent without a local PID although `@ProcessId` is present), for `UiNode::id()` never reading `"0"`, and for the attribute rule that an architecture which cannot be read is absent rather than the host's. The decisions are written as pure functions over injected inputs so that none of this needs a bus.
  - A local, `#[ignore]`d integration harness driving two sibling PID namespaces via `unshare`, behind a `just` recipe — the same shape as `crates/java-agent/tests/live_fixture.rs` and `just test-java-agent-live`, and like them it **fails loudly** when a prerequisite is missing (user namespaces blocked, a bus daemon not installed) instead of skipping. It is **not** wired into CI here and this change makes no runner decisions; change `evaluate-pidns-tests-in-ci` owns CI adoption and still contains research.
  - Regression: the existing X11 and compositor acceptance lanes must stay green, because they are the only check that an ordinary single-namespace desktop still chooses FD or PID mode and filters as before.
- **Docs:** `dev-docs/platform-linux.md` gains the deployment topology and the identity chain; no user-facing documentation changes.
- **Not in scope, owned elsewhere:** the compositor's abort on a peer it cannot see and its own-window skip in `window_at_point` (`fix-compositor-foreign-pidns-clients`), Wayland capability detection across namespaces and the warning for the silent window-manager bounds fallback in `node.rs:1454` (`wayland-sidecar-capabilities`), the X11 `window_at_point` self-skip and its XRes gate (`x11-window-owner-identity`), CI adoption (`evaluate-pidns-tests-in-ci`). Also out of scope and unfixed by this change: `element_at_point` cannot bridge a native window to an AT-SPI application the daemon cannot see at all, because `_NET_WM_PID` is a client-namespace value while the daemon reports nothing (measured on main and on PR #5, with and without collision). An application co-located with the daemon is not affected by this: its daemon-view PID and its `_NET_WM_PID` are the same number.
