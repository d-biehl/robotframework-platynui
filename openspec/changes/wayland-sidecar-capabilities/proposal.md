# Proposal

## Why

PlatynUI is gaining a supported deployment in which the runtime and the application it drives live in **different PID namespaces** — a Kubernetes sidecar shape: display server, AT-SPI bus daemon and application in one container, the PlatynUI runtime in a sibling container, without `shareProcessNamespace`. Under our own Wayland compositor that deployment silently loses every compositor-backed capability, because the compositor is identified by its **process**: `detect_via_peercred` (`crates/platform-linux-wayland/src/capabilities.rs:62-88`) reads `SO_PEERCRED` from the Wayland socket and resolves `/proc/<pid>/exe`. Across a PID-namespace boundary the kernel reports pid 0, so the lookup cannot work.

Measured live in podman pod `pidns-wl` (compositor + egui app in the app container, CLI in a sibling container, no PID sharing):

- from the app container: `compositor process identified pid=1198 exe=/opt/pbin/platynui-wayland-compositor` → `CompositorType::PlatynUi`;
- from the sidecar: `SO_PEERCRED failed … error=Unknown error -1000` → `CompositorType::Unknown`.

Everything gated on that answer then degrades, and two of the consequences are worse than a missing feature because they **report success**:

- `highlight` prints `Highlighted 1 region(s).`, exits 0, and logs that it did nothing — `highlight.rs:14-17` returns `Ok(())` after a warning.
- With no window manager the AT-SPI provider's `resolve_extents` skips its WM-bounds step (`crates/provider-atspi/src/node.rs:1346-1350`) and falls back to the extents the toolkit reports itself — which a Wayland client can only give relative to its own surface: the Frame reports `@Bounds {0,0,600,500}` where the compositor's own `get_window` says `{10,40,600,500}`. A click by XPath then reports success, lands 40 px too high, and the application does not react. The mechanism is a discarded error: `resolve_window_manager_bounds` (`node.rs:1454-1457`) turns a failing window-manager call — the window lookup (`resolve_window`, `.ok()?` at `:1444`) or the bounds read (`.ok()` at `:1456`) — into `None`, and the toolkit's extents take its place without anything saying so. In the measured sidecar it is the lookup that fails, because an unrecognised compositor's window manager refuses every call (`crates/platform-linux-wayland/src/window_manager/mod.rs:99-110`).

The rest is lost outright but at least visibly: window activation (`no backend implemented yet for compositor Unknown`), `element-at-point`, screenshot, display-config enrichment; input falls back from the control socket to EIS (EIS injection itself works across namespaces). The documented escape hatch does not help either — `scripts/startcompositor.sh:193` exports `XDG_CURRENT_DESKTOP=platynui`, but `detect_via_env` (`capabilities.rs:114-136`) matches only gnome/kde/plasma/hyprland/sway, although `classify_binary_name` has a `platynui` branch (`capabilities.rs:94-95`).

The identity question is the same one the AT-SPI provider faces in `atspi-process-identity`: **who am I / who is that, when PIDs are not comparable**. The answer here is cheaper, because our compositor already has a channel that works across the boundary — the control socket, measured working from the sidecar over an absolute path.

## What Changes

- **Compositor identification stops depending on PID visibility.** The primary check becomes a handshake over the compositor's existing control socket: connect to `PLATYNUI_CONTROL_SOCKET` (else `$XDG_RUNTIME_DIR/$WAYLAND_DISPLAY.control`) and send the existing `status` command (`apps/wayland-compositor/src/control.rs:391`). A compositor that answers with its identity marker is `CompositorType::PlatynUi`, whether or not the peer's PID is visible.
- **The compositor names itself in `status`.** The response gains an explicit identity field (`apps/wayland-compositor/src/control.rs:839-850`), so identification does not rest on "some JSON-lines server answered". The field is additive; the protocol is documented as unversioned v0 (`apps/wayland-compositor/docs/ipc-protocol.md:475-480`), and today's clients ignore unknown fields.
- **`detect_via_env` learns `platynui`.** `XDG_CURRENT_DESKTOP=platynui` maps to `CompositorType::PlatynUi`, closing the gap against `classify_binary_name` and `startcompositor.sh`.
- **`SO_PEERCRED` is demoted to a foreign-compositor heuristic.** It is no longer what decides whether our own compositor is present, and its failure is no longer read as "not PlatynUI". Foreign compositors (Mutter, KWin, sway, Hyprland) keep today's `SO_PEERCRED` + `/proc/<pid>/exe` path and the env fallback. Only the read itself changes: it moves from `rustix::net::sockopt::socket_peercred`, which is undefined behaviour for a peer whose PID reads as `0`, to `nix`'s safe `getsockopt` with `sockopt::PeerCredentials` — the same read `fix-compositor-foreign-pidns-clients` uses in the compositor, with no `unsafe` — and the rustix accessor is banned in `clippy.toml`.
- **An identified PlatynUI session is never silently downgraded to the foreign path.** When the session is identifiably ours (env marker) but the control socket is unusable, the gated capabilities fail with the socket path and the underlying error in the message, instead of pretending to be an unknown compositor — which is the state that produces the silently wrong bounds above.
- **A substituted window geometry is logged; the value itself is unchanged.** `resolve_window_manager_bounds` (`crates/provider-atspi/src/node.rs:1454-1457`) drops the window manager's error — from the window lookup or from the bounds read — and `resolve_extents` answers a real top-level with the toolkit's own extents instead. That fallback **stays** (maintainer decision): it is a best-effort value, and on X11 the toolkit's extents are real screen coordinates. What changes is that it is no longer silent: when the window manager cannot answer for a real top-level, the provider emits a **warning** naming the node and its window, which call failed and the window manager's error (for the PlatynUI compositor that error names the control-socket path), and that the toolkit's extents were used instead. The warning is rate-limited to once per top-level while its window-manager reads keep failing, re-armed by a successful read (design decision 7), so an Inspector refreshing the tree cannot flood the log. On Wayland the fallback is window-relative — the measured `{0,0,600,500}` against the compositor's `{10,40,600,500}` — and the warning is what makes that case diagnosable instead of observable only as a click that misses by the window offset. **This is provider code, and it is in this change on purpose:** the theme here is "a capability that cannot deliver says so instead of passing off a plausible answer", and this is the same silence as `highlight`'s, one consumer further along. The boundary with `atspi-process-identity` stays clean — that change owns process identity and every PID-valued attribute of the AT-SPI provider; this one owns the diagnostics of a top-level window's window-manager-backed geometry. Neither touches the other's code path in `node.rs`.
- **BEHAVIOR CHANGE (deliberate, not breaking a working setup): `highlight` stops reporting success when it is gated off.** A highlight request for a compositor without a highlight backend returns `CapabilityUnavailable` instead of `Ok(())`. `crates/cli/src/commands/highlight.rs:47,59` already propagates the error, so `platynui-cli highlight` starts failing where it printed `Highlighted 1 region(s).` and did nothing; the `Highlight Element` keyword raises instead of passing. No setup that actually highlighted anything changes behavior. `screenshot.rs:33-36` and `window_manager/mod.rs:99-110` were checked for the same pattern: both already return `CapabilityUnavailable`, so they need no behavioral fix.
- **The identification and its basis are logged once per session**, naming the mechanism (control-socket handshake, environment, peer credentials) and the socket path — the same discipline `atspi-process-identity` applies to its mode decision, so a silent degradation is visible in a log instead of only in wrong coordinates.
- **Depends on `fix-compositor-foreign-pidns-clients` landing first.** Measured: a client whose PID the compositor cannot see makes `window_pid` (`apps/wayland-compositor/src/control.rs:1270-1278`) go through `client.get_credentials`, and `wayland-backend-0.3.15/src/rs/server_impl/client.rs:314` panics in `socket_peercred(…).expect("getsockopt failed!?")`; the poisoned state then aborts the process. One `list_windows` from such a client killed the compositor and with it the whole session (isolated: a foreign client that only maps a window stays alive for 15 s; a single `list_windows` → dead). Identifying the compositor from a sidecar makes the runtime call `list_windows` on every window query, so shipping this change first would convert today's silent degradation into a reproducible crash. The handshake command itself is safe — `build_status_response` (`control.rs:819-850`) never builds `WindowInfo` and so never reaches `window_pid`.

Two things that used to be recorded here as unowned divergences have moved: the compositor's missing own-window skip in `window_at_point` is now owned by `fix-compositor-foreign-pidns-clients`, which adds the skip, and the silent bounds fallback is made visible here (the bullet above; the fallback value itself stays). What stays out of scope, recorded in `design.md` as a known divergence, is that `window --list`'s default expression `//control:Window` matches nothing against AT-SPI/AccessKit, whose top level is `control:Frame` — measured inside the application container too, so unrelated to namespaces and to this change.

## Capabilities

### New Capabilities

- `wayland-compositor-detection`: how the Wayland backend decides which compositor it is talking to and what a capability does when that answer does not support it. Covers: identification must not depend on the peer process being visible; an identified PlatynUI session is not downgraded when its control channel fails; a gated capability reports unavailable instead of reporting success; a window geometry the window manager could not supply keeps its best-effort fallback but is reported in the log; the identification and its basis are recorded once per session.

### Modified Capabilities

None. The related specs were read in full and none of their requirements changes:

- `element-at-point` — this change makes hit-test *available* in the sidecar, which the spec already covers ("Hit-test reports 'unsupported' rather than guessing"). The compositor's missing own-window skip violated "Hit-test excludes the host process's own UI"; closing that is `fix-compositor-foreign-pidns-clients`, which makes the compositor skip the caller's own windows in `window_at_point` — the only side that sees both the requesting client and the surface. The requirement text itself is rewritten by `x11-window-owner-identity`, and the AT-SPI provider's own guard is removed by `atspi-process-identity`, so ownership is decided once, by the window system. Nothing of that is owned here.
- `compositor-popup-geometry`, `compositor-modifier-state` — both already route through the control socket and are unaffected by how the compositor is identified. `compositor-modifier-state` already phrases its Inspector rule as "when the session provides a PlatynUI control socket", which is exactly the criterion this change adopts for detection.
- `per-runtime-platform-lifecycle`, `runtime-session-config` — the Wayland backend keeps its process-global session state and gains no new configuration key; the detection result stays where it lives today (`connection.rs:220-231`).

## Impact

- **Rust, `crates/platform-linux-wayland`** (Linux only; the crate is `#[cfg(target_os = "linux")]` throughout):
  - `src/capabilities.rs` — the detection order, the control-socket handshake, the `platynui` branch in `detect_via_env`, a decision function that is pure over injected inputs so it can be unit-tested without a compositor, and the `SO_PEERCRED` read through `nix` instead of `rustix`, without `unsafe`.
  - `Cargo.toml` — a direct `nix` dependency with the `socket` feature, the same one the compositor gains in `fix-compositor-foreign-pidns-clients`; `rustix` loses its `net` feature, which only this call used.
  - `src/connection.rs:243-253` — `connect_and_enumerate` calls `detect_compositor`; the handshake result and the log line are produced here, before the registry roundtrip.
  - `src/highlight.rs:14-17,33-35` — the fail-open gate.
  - `src/control_ipc.rs` — reused as-is for the handshake; it already names the socket path in its connect error (`:16-19`).
  - `src/lib.rs:12-15,63-67` — module docs still say detection happens "via `SO_PEERCRED`".
- **Workspace lint configuration**: `clippy.toml` gains `rustix::net::sockopt::socket_peercred` in the `disallowed-methods` list that `fix-compositor-foreign-pidns-clients` creates; that change leaves the entry to this one because `capabilities.rs:67` still calls the accessor until this change replaces it.
- **Rust, `apps/wayland-compositor`**: the identity field in `build_status_response` (`src/control.rs:819-850`) and its documentation.
- **Rust, `crates/provider-atspi`** (one function, diagnostics only): `resolve_window_manager_bounds` / `resolve_extents` (`src/node.rs:1343-1389`, `:1454-1457`) keep their fallback for a real top-level and emit the rate-limited warning when they take it. No returned value changes. `provider-atspi` is Linux-only — every product links it only under `cfg(target_os = "linux")` (`crates/cli/Cargo.toml`, `packages/native/Cargo.toml`), where it serves both Linux backends, X11 and Wayland; Windows uses the UIA provider and never reaches this code. On X11 the warning appears wherever the X11 window manager cannot resolve a top-level; nothing else changes there. The PID-valued attributes in the same file belong to `atspi-process-identity`, not here.
- **Downstream behavior, no code change**: `crates/cli` (`highlight` now reports the failure it already propagates; `info` prints the real compositor in a sidecar), `apps/inspector` (picker and highlight follow the same gate), input backend selection (`src/input/mod.rs:93-100`) switches from the EIS fallback to the control socket once the compositor is identified — a path never exercised from a sibling namespace in the measurements and therefore an explicit verification step, not an assumption.
- **Docs**: `dev-docs/platform-linux-wayland.md:686,720` ("compositor type detection via `SO_PEERCRED`"), `apps/wayland-compositor/docs/ipc-protocol.md:73-119` (the `status` field table).
- **Tests**: unit tests for the detection decision in `crates/platform-linux-wayland`; a control-socket handshake test against a real compositor process; a test in `crates/provider-atspi` that a real top-level whose window-manager call fails keeps the toolkit's rectangle and emits exactly one warning naming the window and the failure; and a local, `#[ignore]`d namespace test plus a `just` recipe that runs the compositor in one PID namespace and the detection from a sibling namespace (`unshare`-based, no container runtime). A missing prerequisite — user namespaces blocked, `unshare` absent, the compositor or CLI binary not built — fails that test with the prerequisite named; it never skips (the rule of `crates/java-agent/tests/live_fixture.rs` and `justfile:403-404`). Taking any namespace test into CI is deliberately deferred to `evaluate-pidns-tests-in-ci`.
- **Native rebuild**: no Python or Robot Framework API changes, but the behavior reaches Python only through `packages/native`, so any RF-level verification needs `just build-native` first. No `uv`-side change.
- **Platform/provider status**: Linux only, and Wayland in substance. The README's platform table claims the full capability set works under the PlatynUI compositor (`README.md:98`); this change is what makes that claim hold when the runtime does not share the application's PID namespace. Windows, macOS and the mock are untouched. X11 behaves as before apart from the new bounds-fallback warning, which it shares through `provider-atspi` — X11's own identity problem is `x11-window-owner-identity`.
