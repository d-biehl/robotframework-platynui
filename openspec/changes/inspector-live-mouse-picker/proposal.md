## Why

To read the accessibility tree of a running application, you first have to *find* the element you care about in it — and today the Inspector only offers top-down navigation and XPath search. Both require you to already know something about the target (its role, its name, roughly where it sits in the hierarchy). The fastest way a human identifies a control is by *pointing at it*: "that button, right there." Accessibility Insights for Windows made this the primary workflow — hover the mouse over any control, and the tool reveals it. PlatynUI has no equivalent. A live "pick element under the mouse" mode closes the gap between "I can see the control on screen" and "I have it selected in the Inspector," which is the single most common thing a user wants when they open the Inspector at all.

## What Changes

- **Live mouse-picking mode in the Inspector.** Behind an explicit on/off **toggle**, while the user holds a **configurable** modifier combination (default **Ctrl+Alt+Shift**), the Inspector continuously resolves the UI element under the mouse cursor, selects it in the tree, shows its attributes, and highlights it on screen — following the mouse as it moves, and stopping when the modifiers are released. This mirrors the Accessibility Insights live-inspect experience. It is a *held-modifier* mode (a continuous state, not a one-shot chord): while armed, each tick asks "is the configured combination down right now?" and, if so, picks whatever is under the pointer. The toggle keeps the Inspector from watching the keyboard unless the user has opted in.
- **A new hit-test (element-at-point) capability in the core.** Today the UI tree is strictly top-down — a provider answers `get_nodes(parent) → children` and nothing maps a screen coordinate back to a node. This change introduces an optional reverse lookup ("what element is at this point?") that each provider answers with its native facility (UIA `ElementFromPoint`, AT-SPI `Component.GetAccessibleAtPoint`), with the mock provider answering geometrically for tests. The resolved node feeds into the Inspector's **existing** reveal-and-select machinery (which already walks a node's parent chain to sync the tree) and its **existing** highlight overlay — so the "map result into the tree" half is reuse, not new code.
- **Explicit capability gating.** The picker only works where two things are true at once: the platform can report the **real, live cursor position** and can **hit-test** a point. Where either is missing, the picker is cleanly **disabled/greyed out** in the UI rather than misbehaving. To make that gating honest, cursor-position reporting on backends that cannot observe the physical pointer is changed to surface an explicit "unavailable" signal instead of a misleading `(0, 0)`.
- **Modifier-state reading, Inspector-internal, per platform.** Detecting the held modifiers is done inside the Inspector (not promoted to a shared core/platform trait), in a few lines per platform: X11 already gets the modifier mask from the same `query_pointer` call it uses for the cursor position; Windows polls `GetAsyncKeyState`; the PlatynUI test compositor reports modifiers over its existing control protocol.

Not BREAKING at the API level: the hit-test method is additive (new optional provider method with a default of "unsupported"), and the Inspector change is additive UI/behavior. The one behavior change to watch is that `pointer_position()` on backends that only track injected motion moves from returning `(0, 0)` to returning an "unavailable" error (see Impact).

## Capabilities

### New Capabilities
- `element-at-point`: the core reverse-lookup contract — given a screen point, return the deepest UI node at that point (or nothing). Covers the provider-level method and its default "unsupported" behavior, the per-provider resolution strategy (UIA native, AT-SPI top-window-then-descend in window coordinates, mock geometric), and the z-order / coordinate-system rules that make the answer correct.
- `inspector-live-mouse-picker`: the Inspector-side feature — the held-Ctrl+Alt+Shift poll loop; per-tick read of cursor position + modifier state; resolving the element and driving the existing reveal/select/highlight; live-follow while held and stop on release; and the capability gating (picker disabled where cursor position or hit-test is unavailable, with a discoverable toggle/affordance and status hint).

## Impact

- **Layers touched:** Rust core (`crates/core` — the provider/hit-test trait method, plus a `window_at_point` capability on the `WindowManager` trait), the real providers (`crates/provider-windows-uia`, `crates/provider-atspi`) and `crates/provider-mock`, the X11 window manager (`crates/platform-linux-x11` — EWMH stacking) for AT-SPI window selection, the runtime surface that exposes hit-test and pointer-position (`crates/runtime`), the PlatynUI test compositor and its Wayland platform control protocol (`apps/wayland-compositor`, `crates/platform-linux-wayland`) for `window_at_point` and modifier reporting, and the Inspector app (`apps/inspector`). No Python/Robot Framework surface is required for the picker itself — the cursor position is already exposed as `Get Pointer Position`. **Native rebuild:** only if the runtime/provider hit-test surface is exercised from Python (not needed for the Inspector binary, which links the providers directly).
- **Platform / provider support (see README support table):**
  - **Windows / UIA — full.** `ElementFromPoint` + real `GetCursorPos`-backed position + `GetAsyncKeyState` modifiers.
  - **Linux X11 / AT-SPI — full.** Real `query_pointer` position *and* modifier mask from one call; hit-test resolves window-level z-order from the window manager (EWMH stacking) and in-window z-order from AT-SPI (`get_accessible_at_point` descent in window coordinates, with `Component.Layer`/`MDIZOrder` disambiguating overlapping popups). AT-SPI's per-level D-Bus round-trips are the latency cost, not a blocker.
  - **PlatynUI test compositor (Wayland) — full.** We own the pointer and keyboard, so real cursor position (via the control socket's `get_pointer_position`) and modifiers (control-protocol addition) are both available; hit-test via AT-SPI.
  - **Generic Wayland (KDE / GNOME / Hyprland / Sway) — NOT supported for now.** Blocked at *both* ends: the EIS/portal/virtual-input backends only know a dead-reckoning shadow of injected motion, not the physical pointer, so there is no live cursor position; the hotkey side is therefore moot. The picker is disabled there. Future work (out of scope, do not implement): the `query_compositor_pointer_position` stub in `crates/platform-linux-wayland/src/input/eis.rs` already points at "GNOME/KDE extensions" for cursor position, and the XDG `GlobalShortcuts` portal (KDE, GNOME 48+, Hyprland) — optionally with a portal backend in our own compositor — is the eventual cross-desktop hotkey path.
  - **macOS / AX — deferred.** `AXUIElementCopyElementAtPosition` would make hit-test trivial, but the AX provider is a stub today, so the picker is disabled on macOS until that lands.
- **Dependencies:** no new external crate. The hotkey crate route (e.g. `global-hotkey`) was rejected: a held-modifier mode is a state poll, not a discrete registered chord, so `RegisterHotKey`/`XGrabKey`-style APIs are the wrong model; per-platform reads (`GetAsyncKeyState`, X11 `query_pointer` mask, compositor control protocol) are a few lines each and a better fit. Windows modifier polling uses `windows`/`winapi` bindings the Windows platform crate already carries.
- **Behavior change to flag:** `pointer_position()` on backends that cannot observe the physical pointer (generic-Wayland EIS/virtual-input) changes from returning `(0, 0)` to returning `CapabilityUnavailable`. This is the correct contract (a silent `(0, 0)` would make the picker jump the selection to the screen corner), but any caller currently relying on the `(0, 0)` fallback must be checked — in practice only the new picker consumes this distinction.
- **Tests (Rust nextest, per dev-docs/testing-strategy.md):** hit-test unit/contract tests against the mock provider (deepest-node-at-point, z-order, miss returns nothing, unsupported default); provider-level hit-test verified on real providers via the existing acceptance lane (egui app in the compositor/X session); Inspector picker logic (the poll-tick decision: modifiers-held + valid position → resolve + reveal; gating when unavailable) kept in a pure, unit-testable module, with the interactive live-follow verified by running the Inspector.
- **Docs:** `dev-docs/inspector.md` (new picker feature and its platform gating) and the README platform-support table (a picker row, or a note on the existing Inspector row).
